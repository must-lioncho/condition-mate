# 컨디션 메이트 (Condition Mate)

ConditionMate의 BGM 관리를 "컨디션 메이트(Condition Mate)"라는 동반자로 설계한 문서입니다. 사용자의 작업 상황 전체를 함께 읽고, 거기에 딱 맞는 음악적 연출을 만들어 단조로운 배경음이 아니라 기복 있는 흐름으로 컨디션과 액티비티를 끌어올립니다.

연출 기복을 만드는 메커니즘은 RimWorld의 "스토리텔러(Storyteller)"에서 빌려옵니다. 스토리텔러는 게임 상황을 읽어 사건의 리듬(루틴/랜덤)을 결정합니다. 다만 컨디션 메이트가 지향하는 관계는 게임을 내려다보는 연출자가 아니라, 아래 [0]의 동반자상입니다.

## [0] 이름과 관계 철학: 왜 "메이트"인가

같은 "곁에서 돕는 존재"라도 관계의 성격은 다릅니다. 컨디션 메이트는 다음 대비 속에서 "메이트"를 지향합니다.

- 코치(coach) — 현장에 같이 있지만 주도권을 가진다. 사용자를 끌고 가며 지시한다.
- 로드 매니저(road manager) — 주도권이 없고 서포트만 한다. 시키는 것을 받쳐줄 뿐이다.
- 메이트(mate) — 극도의 스트레스와 신체적 압박을 같이 견디며, 내 등을 맡길 수 있는 존재. 강한 전투에서의 전우애(戰友愛)를 목표로 한다.

즉 컨디션 메이트는 사용자를 위에서 끌고 가지도(코치), 뒤에서 받치기만 하지도(로드 매니저) 않습니다. 같은 압박을 함께 견디는 전우로서, 밀어줄 때 같이 밀고 쉬어갈 때 같이 쉬며 곁을 지킵니다. 이 관계 톤이 아래 모든 설계 결정(연출의 강도·페이싱, Discord 소통의 어조, 강제 사건의 절제)의 기준입니다.

기준 코드와 선행 문서:

- `.doc/bgm-management.md` — 현재 BGM 재생 조건·상태 머신·씬 곡 전략(이 문서의 토대)
- `Sources/ConditionMate/Audio/ConditionDirector.swift` — WARMUP/SUSTAIN/RELEASE 상태 머신과 트랙 선택(실행 계층)
- `Sources/ConditionMate/Audio/AudioEngine.swift` — 실제 재생·크로스페이드
- `Sources/ConditionMate/Audio/BPMLibrary.swift` — BPM·키워드 기반 트랙 조회
- `Sources/ConditionMate/Core/PluginStore.swift` — 플러그인 연결/검증 모델(claude-desktop 선례)
- `Sources/ConditionMate/Core/WorkerRegistry.swift` — owner별 워커 등록/해제
- `Sources/ConditionMate/AppDelegate.swift` — 1Hz 하트비트 게이팅, `claude -p` 오케스트레이션, 채팅

## [1] 아키텍처: 메이트는 "판단 계층", 디렉터는 "실행 계층"

관계는 전우(메이트)지만, 소프트웨어 구조에서는 판단과 실행을 분리합니다. 메이트는 "지금 무엇이 필요한지"만 판단해 의도(Cue)를 내리고, 실제 BGM 처리는 기존 디렉터가 합니다. (RimWorld 스토리텔러가 사건을 결정하고 게임 엔진이 처리하는 것과 같은 층위 분리.)

- 메이트(Mate) — 판단 계층. 상황 전체(시간/요일/활동/외부 신호)를 읽어 "지금 어떤 음악적 사건(Cue)을 줄지"를 결정한다. 직접 오디오를 만지지 않는다.
- 디렉터(ConditionDirector) — 실행 계층. 메이트가 내린 Cue를 받아 목표 BPM·프로파일 밴드·씬 곡으로 변환하고 상태 머신을 돌린다. 기존 코드가 거의 그대로 실행자가 된다.
- 오디오 엔진(AudioEngine) — 기계 계층. 실제 재생·크로스페이드.

이 분리의 핵심 효과는 다음과 같습니다.

- 기존의 잘 튜닝된 적응 제어(활동률→템포)는 그대로 보존된다. 디렉터는 컨디션 메이트 플러그인 소유이므로, 설치되면 그 적응 제어가 BGM의 "기본 기능"으로 돌고, 메이트(루틴/랜덤)는 그 위에 얹히는 선택적 상위 두뇌다. 메이트가 No-op(기본 Cue)이면 디렉터는 평소의 자율 적응대로 동작한다. (플러그인 미설치면 디렉터 자체가 꺼져 무음.)
- 메이트는 교체 가능하다. 루틴 메이트, 랜덤 메이트처럼 서로 다른 성격의 연출가를 같은 디렉터 위에 갈아 끼울 수 있다.
- 메이트는 디렉터의 내부 상태 머신을 몰라도 된다. "지금은 고조 구간으로 가라", "회복시켜라", "이 씬 곡을 틀어라" 수준의 의도만 전달한다.

### 1.1 Cue: 메이트가 디렉터에게 내리는 지시

메이트의 출력은 "연출 지시(Cue)"입니다. Cue는 다음 중 하나 이상을 담는 의도 표현입니다(구체 BPM 숫자가 아니라 의도).

- 무드 전환 — 프로파일 밴드를 바꾼다(chill/steady/focus/hype). 기존 `BGMProfile`/`director.applyProfile(...)`을 재사용.
- 에너지 편향 — 같은 밴드 안에서 더 끌어올릴지(가속 우세) 진정시킬지(회복 우세)의 성향.
- 강제 사건 — "지금 RELEASE로 떨어뜨려 회복 구간", "지금 hype 스파이크", "지금 씬 곡 X로 전환" 같은 일회성 강제.
- 씬 곡 지정 — 키워드로 특정 곡 고정(기존 `library.track(matchingKeyword:)` 재사용).
- 멘트 — Discord로 사용자에게 보낼 한 줄 내레이션(선택).

디렉터에는 Cue를 받는 진입점(예: `apply(cue:)`)을 하나 추가합니다. 내부적으로는 이미 존재하는 `applyProfile`, 강제 트랙 전환, RELEASE 전이 로직을 호출하는 얇은 어댑터입니다. 기존 자율 tick은 Cue가 "에너지 편향"만 줬을 때의 기본 경로로 계속 돕니다.

## [2] 플러그인화: 설치형(toggle) — 폴더가 아니라 채널이 연결이다

컨디션 메이트는 워커 시스템 안의 독립 플러그인입니다. 다만 연결 모델은 `claude-desktop`(폴더 연결)과 다릅니다. 메이트의 작업 파일(스케줄·이벤트·프롬프트·Discord 큐)은 사용자가 지정할 외부 폴더가 아니라 앱이 직접 만들고 쓰는 내부 자원이므로, 폴더를 고를 이유가 없습니다. 그래서 두 가지를 분리합니다.

- 설치(install) = 기본 기능 켜기. 설치하면 BGM 디렉터가 함께 켜져 적응형 BGM 컨디션 관리가 동작한다. 자원은 앱 데이터 폴더(`AppPaths`)에 자동 보관. 폴더 선택·검증 단계 없음.
- 채널 연결(Discord) = 강화. 설치 위에 얹는 양방향 소통·정보 수집 통로([6]). 메이트에게 의미 있는 "연결"은 폴더가 아니라 이 채널이다.

### 2.1 PluginStore 빌트인 (kind = toggle)

`PluginStore`는 플러그인 종류를 `Kind`로 구분합니다. `folder`(claude-desktop, 폴더 연결+검증)와 `toggle`(condition-mate, 설치=연결).

- id: `condition-mate`, name: "컨디션 메이트", kind: `toggle`
- 상태: 설치되면 `valid`(설치됨), 아니면 `disconnected`(미설치). 설치 여부는 `Settings.pluginInstalled[id]`(JSON 영속)로 저장.
- 기본 설치됨: `PluginStore.defaultInstalled`에 `condition-mate`가 들어 있어 첫 실행부터 설치 상태(BGM 즉시 동작). 사용자가 제거하면 그 상태가 영속된다.
- 설치/제거: `install(pluginId:)`/`uninstall(pluginId:)`. 폴더 plugin에는 no-op.
- 대시보드 API: `POST /api/plugin/install`·`/api/plugin/uninstall`. 카드는 `kind=='toggle'`이면 폴더 연결 대신 설치/제거 버튼을 렌더링한다.

### 2.2 워커 소유권(owner = "condition-mate")

`syncPluginWorkers()`는 설치 시 다음 워커를 등록하고 제거 시 unregister 합니다. 핵심: BGM 디렉터가 더 이상 core 상시 워커가 아니라 이 플러그인 소유입니다.

- `director` — 활동률 기반 BGM 템포 결정(기본 기능). 미설치면 등록 해제 + 하트비트 음악 게이트가 디렉터를 정지시켜 무음.
- `mate-tick` — 메이트 의사결정 루프(30초). 상황을 평가해 다음 Cue를 산출한다. 디렉터의 20초 적응 tick보다 느린 "연출 주기".
- `mate-discord`(4단계) — Discord 인박스 폴링(수신) + 아웃박스 전송(송신).
- `mate-suno`(5단계) — Suno 프롬프트 생성/회수 점검.

### 2.3 코드 폴더 구조

코드는 기존 단일 실행 타깃 안에 폴더로 둡니다: `Sources/ConditionMate/Plugins/ConditionMate/`. SwiftPM 설정 변경 없이 컴파일되고, "폴더 단위 관리" 의도를 충족하며, 메모리 가벼운 단일 바이너리 철학과도 맞습니다. (최상위 `Sources/Plugins`는 `Package.swift` 타깃 경로가 `Sources/ConditionMate` 단일이라 컴파일되지 않으므로 채택하지 않음.)

- `Mate.swift` — `Mate` 프로토콜, `Cue`, `MateContext`
- `MateRegistry.swift` — 사용 가능한 메이트 목록·현재 선택
- `RoutineMate.swift` / `RandomMate.swift` — 두 메이트
- `SunoPromptWriter.swift`(5단계) / `DiscordBridge.swift`(4단계)

### 2.4 자원 폴더(앱 데이터 디렉터리, 자동 생성)

사용자가 고르는 폴더가 아니라 `AppPaths` 아래 자동 생성되는 내부 자원입니다(2~5단계에서 필요 시 생성).

- `<AppPaths>/conditionmate/mates/routine/schedule.json` — 루틴 메이트 스케줄
- `<AppPaths>/conditionmate/mates/random/events.json` — 랜덤 메이트 이벤트 풀
- `<AppPaths>/conditionmate/prompts/` — 생성한 Suno 프롬프트
- `<AppPaths>/conditionmate/inbox/`·`outbox/` — Discord 메시지 큐(파일 기반, [6])
- `<AppPaths>/conditionmate/state.json` — 런타임 상태(마지막 이벤트 시각 등)

### 2.5 메이트 선택 UI

플러그인 카드(대시보드)에서 현재 메이트(루틴/랜덤)를 고릅니다. 선택값은 `Settings`에 `cm.conditionMate`("routine" | "random")로 저장하고, `MateRegistry.current`가 읽어 활성 메이트를 돌려줍니다. 메이트 추가는 `MateRegistry.all`에 한 줄 더하면 됩니다. (2단계 UI)

## [3] 루틴 메이트 (Routine Mate)

시간대·요일·날짜에 따라 정해진 연출을 거는 규칙 기반 메이트입니다. RimWorld의 "정해진 박자로 사건을 주는" 성격에 해당합니다.

### 3.1 스케줄 모델

`schedule.json`은 규칙의 우선순위 목록입니다. 각 규칙은 "조건 → Cue"입니다. 조건은 다음을 조합합니다.

- 시간대(예: 09:00~12:00)
- 요일(월~금 / 주말 / 특정 요일)
- 날짜(특정 일자, 월말 등 선택적)

규칙은 위에서부터 평가하고, 가장 먼저 매칭되는 규칙의 Cue를 적용합니다. 매칭이 없으면 기본 Cue(디렉터 자율)로 둡니다.

### 3.2 기본 프리셋(예시)

- 평일 오전(시작~정착) — 가벼운 무드에서 서서히 끌어올림. chill→steady. 씬 곡 오프닝(096) 전략과 자연스럽게 이어짐.
- 평일 오후(딥워크) — focus 밴드, 가속 편향. 집중 구간 유지.
- 늦은 오후(피로 구간) — 회복 편향을 높여 RELEASE 전이가 더 쉽게 일어나게 함.
- 금요일 저녁 — hype 편향. 한 주 마무리의 고조 연출.
- 주말 — 전반적으로 낮은 강도(chill 우세), 강제 사건 빈도 낮춤.

프리셋은 `schedule.json`에 기록되어 코드 변경 없이 사용자가 수정·확장할 수 있습니다.

### 3.3 동작

`mate-tick` 워커가 현재 시각을 읽어 스케줄을 평가하고, 직전과 달라진 무드/편향이 있을 때만 Cue를 디렉터에 전달합니다(불필요한 잦은 전환 방지 — 디렉터의 min-dwell과 같은 사상). 전환 시 Discord로 한 줄 내레이션을 보낼 수 있습니다(선택).

## [4] 랜덤 메이트 (Random Mate)

RimWorld의 "Randy Random"에 해당합니다. 일정 박자로 이벤트 풀에서 가중 추첨해 예측 불가능한 기복을 만듭니다. 단조로움을 깨 액티비티를 자극하는 것이 목적입니다.

### 4.1 이벤트 풀

`events.json`은 이벤트 목록입니다. 각 이벤트는 다음을 가집니다.

- 종류 — 스프린트(갑작스러운 가속·hype 스파이크), 정비(강제 회복 구간), 깜짝 곡(예상 밖 씬 곡), 무드 전환 등
- 가중치 — 추첨 확률의 기본 비중
- 컨텍스트 조건(선택) — 현재 활동/시간대에 따라 가중치를 보정(예: 활동이 정체됐을 때 스프린트 가중↑, 장시간 고강도 뒤엔 정비 가중↑)
- 쿨다운 — 같은 이벤트가 너무 자주 나오지 않도록 최소 재발 간격

### 4.2 추첨과 페이싱

- 랜덤 메이트는 매 tick마다 사건을 던지지 않습니다. "다음 사건까지의 간격"을 두고, 그 간격이 지나면 컨텍스트 보정된 가중치로 한 이벤트를 추첨해 Cue로 내립니다.
- 결정성/재현 주의: 코드 환경에서 무작위 사용에 제약이 있을 수 있으므로, 시드는 메이트 상태(`state.json`)에 보관해 재시작 후에도 페이싱이 자연스럽게 이어지게 합니다.
- 추첨 결과는 Discord 내레이션과 잘 어울립니다("깜짝 이벤트: 스프린트 구간 — 5분만 몰아칩시다").

### 4.3 안전장치

- 강제 사건이 사용자의 실제 흐름을 해치지 않도록, 유휴/회의 등 부적절한 상황에서는 사건을 보류합니다(컨텍스트 게이트).
- 연속 강제 사건 사이에 최소 휴지(global cooldown)를 둡니다.

## [5] Suno 프롬프트 생성과 트랙 회수

메이트는 재생뿐 아니라 "앞으로 생성할 곡"의 Suno 프롬프트를 만드는 역할도 맡습니다([1] 요구사항). 현재 라이브러리에 원하는 무드/BPM의 곡이 부족할 때, 메이트가 그 빈자리를 메울 프롬프트를 생성합니다.

### 5.1 생성 트리거

- 라이브러리 공백 감지 — 메이트가 원하는 무드/BPM 대역에 가까운 트랙이 라이브러리에 없을 때(`BPMLibrary` 조회로 판단), 그 대역을 채울 프롬프트를 만든다.
- 사용자 요청 — Discord로 "더 신나는 곡 만들어줘" 같은 요청이 오면 그에 맞는 프롬프트를 만든다.
- 정기 보충 — 루틴/랜덤 메이트가 자주 쓰는 씬에 대해 변주 곡을 미리 확보.

### 5.2 프롬프트 작성

프롬프트 본문은 `claude -p`를 재사용해 생성합니다(앱은 이미 `resolveClaude()` + `bash -lc` 패턴 보유). 입력으로 현재 컨텍스트(무드, 목표 BPM 대역, 시간대, 최근 활동, Discord로 수집한 사용자 취향)를 주고, Suno에 바로 붙일 수 있는 텍스트(장르·BPM·분위기·악기·길이·가사 유무)를 받습니다. 결과는 `<root>/prompts/<timestamp>-<mood>.txt`로 저장하고, 대시보드/Discord로 사용자에게 알립니다.

### 5.3 생성과 회수

- 실제 Suno 생성: Suno의 공식 공개 API 여부가 불확실하므로 초기에는 "프롬프트 생성까지 자동, 실제 생성은 사용자가 Suno에서 수동" 경로를 기본으로 한다. 사용자가 만든 곡을 음악 폴더에 떨구면 기존 `BPMLibrary.load(...)`가 다음 스캔에서 집어 올린다.
- 자동화 여지: 추후 Suno(또는 대체 모델) API가 확인되면 `SunoPromptWriter` 뒤에 생성 호출을 붙이는 seam을 둔다. 파일명에 BPM이 들어가야 라이브러리가 인식하므로(현 규칙), 회수 단계에서 파일명 규칙을 맞춘다.

이 단계는 [1]~[4]가 동작한 뒤 얹는 확장입니다. 초기 구현에서는 seam(프롬프트 생성 + 출력 폴더 + 회수 점검 워커)까지만 만들고 실제 생성 호출은 비웁니다.

## [6] Discord 인터페이스 (양방향 소통)

[3] 요구사항: 액티비티 데이터만으로는 메이트가 상황을 충분히 알 수 없으므로(RimWorld 스토리텔러가 세이브/로드 횟수까지 읽듯), 메이트와 사용자가 소통해 정보를 얻는 채널을 만든다. 채널은 Discord.

### 6.1 메이트가 Discord로 얻고 싶은 정보

활동 모니터(키/마우스/앱/도메인)가 못 보는 신호들입니다.

- 주관적 컨디션 — "지금 피곤", "각성됨", "막힘", "흐름 탐"
- 의도/요청 — "신나는 거", "조용히", "딥워크 들어감", "곧 회의"
- 맥락 사건 — RimWorld의 세이브/로드 빈도 비유에 해당하는 "방금 큰 작업 끝냄", "리뷰 반려됨" 같은 비-OS 사건
- 피드백 — 방금 연출/곡에 대한 좋아요/싫어요(기존 dislike 모델과 연결)

이 신호는 `MateContext`에 합류해 루틴/랜덤 메이트의 판단과 Suno 프롬프트 생성에 쓰입니다.

### 6.2 구현 방식 — 추천안

- 송신(메이트→사용자): Discord Incoming Webhook으로 HTTPS POST. 봇 없이 URL 하나로 충분하고 가장 단순함. 메이트의 내레이션·생성 알림·질문을 보냄.
- 수신(사용자→메이트): 두 가지 후보가 있다.
  - 후보 A(추천, 가벼움): 봇 브리지 스크립트를 플러그인 폴더에 둔다(앱의 기존 "스크립트 + 파일 플래그" 패턴: qa-scan.sh 류와 동일 사상). 작은 Discord 봇이 게이트웨이에 붙어 사용자가 보낸 메시지를 `<root>/inbox/`에 파일로 적고, 앱의 `mate-discord` 워커가 인박스를 폴링해 소비한다. 송신은 앱이 직접 outbox/webhook으로.
  - 후보 B(순수 Swift): 앱 안에서 Discord Gateway WebSocket을 직접 구현. 의존성은 없지만 게이트웨이/하트비트/재연결을 직접 다뤄야 해 메뉴바 앱에는 무겁다.

추천은 후보 A입니다. 송신은 순수 Swift(URLSession POST), 수신은 폴더 인박스를 통한 브리지. 이렇게 하면 앱 본체는 파일 IO만 하면 되고(기존 워커 패턴과 일치), 봇 토큰 같은 민감 정보는 브리지 스크립트와 설정에만 둡니다.

### 6.3 설정과 보안

- `cm.discordWebhookURL` — 송신용 웹훅 URL(Settings)
- 봇 토큰 — 브리지 스크립트의 환경변수/로컬 설정 파일에 두고 저장소에 커밋하지 않음(.gitignore)
- 인박스 메시지는 신뢰 경계로 다룬다(외부 입력). 메이트는 인박스 내용을 명령이 아니라 "신호"로만 받아들이고, 위험한 행위(파일 삭제 등)로 직접 연결하지 않는다.

## [7] 하트비트·데이터 흐름 통합

1Hz `onHeartbeat`에 다음을 더합니다.

- 설치 여부(`pluginStore.isConnected("condition-mate")`)를 확인한다.
- 설치 시: 음악 게이트가 평소대로 디렉터를 구동(BGM 동작)하고, `mate-tick` 주기(30초)에 활성 메이트(`MateRegistry.current`)에게 `MateContext`를 넘겨 다음 Cue를 받아 `director.apply(cue:)`로 전달한다. `mate-discord`/`mate-suno`는 각자 주기로 동작.
- 미설치 시: 음악 게이트가 디렉터를 정지시킨다 — BGM은 완전히 무음(디렉터가 플러그인 소유이므로). 메이트 계층도 비활성.

`MateContext`가 모으는 입력:

- 활동 — `activity.activityRate`, idle 여부, 현재 앱/도메인/가치 tier
- 시간 — 현재 시각·요일, 오늘 누적 토탈 시간
- 디렉터 상태 — 현재 phase/targetBPM/프로파일
- 외부 신호 — Discord 인박스에서 들어온 컨디션/요청/피드백
- 라이브러리 — 사용 가능한 BPM 대역(공백 판단용)

## [8] 설정 키와 영속화

`Settings`(JSON 파일 영속)에 추가하는 키:

- `cm.pluginInstalled` — 토글형 플러그인 설치 상태 dict(pluginId → bool). `condition-mate`는 기본 설치(`PluginStore.defaultInstalled`). 구현 완료.
- `cm.conditionMate` — 활성 메이트 식별자("routine" | "random"). 기본 "routine". 구현 완료.
- `cm.discordWebhookURL` — Discord 송신 웹훅 URL. 기본 빈 문자열. (4단계)

런타임 상태는 자원 폴더의 `state.json`에 둡니다(마지막 이벤트 시각, 랜덤 시드, 마지막 적용 Cue 등).

## [9] 단계별 구현 계획

규모가 크므로 작동 가능한 단위로 나눠 점진적으로 올립니다.

- 1단계 — 골격: `Mate` 프로토콜·`Cue`·`MateContext`·`MateRegistry`, 디렉터에 `apply(cue:)` 어댑터. PluginStore에 `condition-mate` 빌트인(toggle, 기본 설치)·install/uninstall, `syncPluginWorkers`가 `director`+`mate-tick`을 플러그인 소유로 등록, 하트비트 음악 게이트를 설치 여부로 묶음. 메이트는 우선 "기본 Cue만 내리는 No-op"으로 빌드/설치/제거 검증.
- 2단계 — 루틴 메이트: `schedule.json` 로딩과 평가, 기본 프리셋, 무드/편향 전환을 디렉터에 반영. 대시보드 메이트 선택 UI.
- 3단계 — 랜덤 메이트: 이벤트 풀·가중 추첨·페이싱·쿨다운·컨텍스트 게이트.
- 4단계 — Discord: 송신(웹훅) 먼저, 이어서 수신(브리지 + 인박스 폴링). `MateContext`에 외부 신호 합류.
- 5단계 — Suno: 프롬프트 생성(`claude -p`)·출력 폴더·회수 점검 워커. 실제 생성은 seam만.

각 단계는 빌드·연결·해제가 깨지지 않는지 확인한 뒤 다음으로 넘어갑니다.

## [10] 확정된 결정 사항

사용자 확인을 거쳐 다음으로 확정했습니다.

- 코드 폴더 위치: `Sources/ConditionMate/Plugins/ConditionMate/`. SwiftPM 설정 변경 없이 단일 실행 타깃 안에서 바로 컴파일된다.
- 연결 모델: 폴더 연결 폐기 → 설치형(toggle). 설치 = BGM 디렉터 켜기(기본 기능), 자원은 앱 데이터 폴더 자동 보관. 컨디션 메이트는 기본 설치됨(첫 실행부터 BGM 동작), 제거하면 BGM도 꺼진다.
- BGM 디렉터 소유권: core 상시 워커 → 컨디션 메이트 플러그인 소유. 미설치 시 무음.
- Discord(채널 연결) = 강화. 설치 위에 얹는 양방향 소통. 수신은 브리지 스크립트 + 파일 인박스, 송신은 순수 Swift 웹훅 POST. (4단계)
- Suno 범위: 프롬프트 생성까지만 — `claude -p`로 프롬프트를 만들어 `prompts/`에 저장·알림. 실제 생성은 수동, 곡을 음악 폴더에 떨구면 라이브러리가 회수. 생성 호출은 seam만. (5단계)

## [11] 진행 현황

- 1단계(골격) — 완료·검증. `Mate`/`Cue`/`MateContext`/`MateRegistry`, 디렉터 `apply(cue:)`, PluginStore `condition-mate`(toggle, 기본 설치)·install/uninstall, `syncPluginWorkers`가 `director`+`mate-tick`을 플러그인 소유로 등록, 하트비트 음악 게이트를 설치 여부로 묶음, 대시보드 설치/제거 UI. 검증: 첫 실행 기본 설치(BGM 동작) → 제거 시 BGM·워커 정지 → 재설치 복귀 → 제거 상태 재시작 후 영속까지 확인. 루틴·랜덤 메이트는 기본 Cue만 내리는 골격(2~3단계에서 `decide` 구현).
- 2~5단계 — 미착수.
