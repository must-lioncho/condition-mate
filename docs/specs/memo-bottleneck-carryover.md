# 메모패드 바틀넥(`!`) 줄 이월 — 사양

작성: 2026-09-01 KST · 작성자 `lion-condition-mate-pm` · 상태: **구현 전, 라이언 확인 대기**
대상 코드: `Sources/ConditionMate/Dashboard/MemoPad.swift`
관련: `Sources/ConditionMate/Core/MemoStore.swift`, `Sources/ConditionMate/Core/ReviewStore.swift`,
`Sources/ConditionMate/Dashboard/DashboardContent.swift`

이 문서는 라이언의 일감 "메모패드에서 `!` 표시한 줄이 다음 루프로 이월되게 하라" 에 대한 답이다.
산출물 다섯 개를 순서대로 채운다. 코드는 아직 고치지 않았다.

---

## 먼저 — 이름 충돌 하나를 갈라 둔다

`docs/loop-definition.md` 는 "루프" 를 **L1~L9 아홉 칸 위임 파이프라인** 으로 정의하고, 스스로를
"Condition Mate 루프의 공식 정의" 라고 선언한다(`docs/loop-definition.md:5`).

라이언이 메모패드 화면을 보며 말한 "루프" 는 **그것이 아니다.** 메모패드의 루프는 보드(트래커)의
스프린트/릴리즈 코드(`26-61`)이고, 코드상 완전히 다른 계층에 있다. 근거:

- `MemoPad.swift:31-33` — "보드(트래커)와 같은 루프가 단위다: 루프 번호는 보드의 스프린트/릴리즈
  코드와 한 일련번호다"
- `MemoPad.swift:2088` — `bgLoop={ cur:(open&&open.code)||'', prev:(rel&&rel.code)||'', cuts:cuts }`
  — `/data.json` 의 열린 스프린트 코드와 릴리즈 컷 시각에서 온다.
- `docs/loop-definition.md` 의 L1~L9 는 `Core/LoopScan.swift` / `Core/LoopHistory.swift` /
  `/loop-engineering` 페이지가 쓰는 것이고, `MemoPad.swift` 는 그 어느 것도 참조하지 않는다.

**두 개는 별개다. 이 문서의 "루프" 는 전부 보드 스프린트 루프(26-61)를 뜻한다.**

## 1. 세 가지 확인 — 실제 파일과 라인

### 1-1. `!` 는 코드에서 무엇인가

**답: 별개 플래그가 아니라 원 클릭 3상태 순환의 세 번째 상태 `block`(바틀넥)이다.** 라이언이 말한
`!` 와 단축키 줄의 "바틀넥" 은 같은 것이다.

| 근거 | 위치 |
|---|---|
| 상태 3종과 화면 마크 정의 — `MARK={todo:'',done:'✓',block:'!'}` | `MemoPad.swift:656` |
| 저장 토큰 — `TOKEN={todo:'- [ ] ',done:'- [x] ',block:'- [!] '}` | `MemoPad.swift:657` |
| 저장 포맷 주석 — `- [!] 할 일   바틀넥(막힘)` | `MemoPad.swift:72` |
| 파싱 — `({' ':'todo','x':'done','!':'block'})[m[1]]` | `MemoPad.swift:1603-1604` |
| 주황(호박)색 — "빨강/녹색은 쓰지 않는다(앱 규칙) — 호박색" | `MemoPad.swift:231` |
| 보기 콤보 라벨 `바틀넥` | `MemoPad.swift:882` |
| CSV 내보내기 라벨 `LABEL={todo:'미완료',done:'완료',block:'바틀넥'}` | `MemoPad.swift:2637` |
| 단축키 줄 원문 "원 클릭 미완료 → 완료 → 바틀넥" | `MemoPad.swift:640` |

파란 체크 + 취소선 줄은 두 개가 겹친 것이다: `done` 상태(파란 원 + 회색 글자,
`MemoPad.swift:227-230`) 와 `⌘⇧S` 취소선(U+0336 결합 문자, `MemoPad.swift:2625`)은 **다른 축**이다.
취소선은 상태가 아니라 글자에 붙는다.

### 1-2. "루프" 는 코드에서 무엇인가

**답: 루프 개념은 이미 있다. 루프를 끝내는 조작도 이미 있다. 없는 것은 이월뿐이다.**

- **화면 상단 `보기 26-61 (3)` 의 정체** — `MemoPad.swift:617`:
  `보기 <b data-cmmemo-view-cr>루프</b> <i data-cmmemo-view-n>2</i> ▾`
  - `26-61` = 지금 도는 보드 루프 코드(`bgLoop.cur`). 라벨 계산은 `MemoPad.swift:1132-1134`.
    세션 단위가 **아니다**.
  - `(3)` = 지금 보이는 **상태 축의 개수**(미완료·완료·바틀넥 셋 다 보임). 줄 수가 아니다.
    `MemoPad.swift:898` (`p.viewN.textContent=on.length`), `MemoPad.swift:882`.

- **루프를 끝내는 조작은 두 개고, 서로 다른 일을 한다.**

  | | 위치 | 하는 일 | 루프 번호를 넘기나 |
  |---|---|---|---|
  | 보드 `Complete loop` 버튼 | `DashboardContent.swift:3630` → `releaseSprintGroup()` `:4286` → `POST /api/sprint/complete` `AppDelegate.swift:7751` → `ReviewStore.completeSprint()` `:1411` | 진짜 컷. 릴리즈 기록 생성, 스프린트 닫기, **미완료 보드 목표를 후속 루프로 이월** | **넘긴다** |
  | 패드 보기 콤보의 `루프 종료` | `MemoPad.swift:987 loopEnd()`, 메뉴 `MemoPad.swift:2982` | 스탬프 없는 **완료 줄에만** `@루프: <코드>` 를 찍어 묻는다 | **안 넘긴다** |

  즉 라이언이 "루프를 끝내면" 이라고 할 때의 조작은 보드의 `Complete loop` 다. 패드 안의
  `루프 종료` 는 이름이 같지만 번호를 전진시키지 않는 부분 동작이다.

- **핵심 비대칭 (이 일감의 진짜 원인).** `Complete loop` 의 확인 문구가 그대로 말한다
  (`DashboardContent.swift:4286`):
  > "완료 목표는 커밋되고, **미완료 목표가 있으면 열린 루프로 이월됩니다**"

  실제로 보드 목표는 이월된다 — `ReviewStore.swift:1440-1452` (`leftover` → `successor` 로
  `goals[i].sprint` 재배정, `carriedTo`/`carriedIds` 로 복원 가능). **메모패드 줄에는 그 이월이
  없다.** 같은 버튼, 같은 순간, 보드 목표만 넘어가고 메모 줄은 넘어가지 않는다.

- **줄이 어느 루프의 것인가** — `loopOf()` `MemoPad.swift:1038-1047`. 2단계: (1) 묻힌 `@루프`
  스탬프가 있으면 그 루프, (2) 없으면 `@생성` 시각이 어느 컷과 컷 사이였나. 컷 시각은 릴리즈의
  `releasedAt`(`bgLoop.cuts`, `MemoPad.swift:2083-2088`).

### 1-3. "사라진다" 의 정확한 의미

**답: 지워지지도, 아카이브로 가지도 않는다. CSS `display:none` 으로 가려질 뿐이고, 저장 텍스트는
한 글자도 안 바뀐다. 체크를 눌러서 사라지는 것이 아니라 루프가 넘어가서 사라진다.**

- 판정 — `MemoPad.swift:2174-2175`:
  ```
  var rold = !blank && !!LCUR && !!rlp && rlp!==LCUR;
  if(rold) row.dataset.lold='1'; else delete row.dataset.lold;
  ```
  줄이 속한 루프가 현재 루프와 다르면 `data-lold` 를 단다. **상태를 전혀 보지 않는다** — 그래서
  `!`(block) 줄도 예외 없이 걸린다.
- 감춤 — `MemoPad.swift:393`: `.cmmemo .cmm-row[data-lold]{ display:none }`
- 되살리는 길 두 개 — `MemoPad.swift:394` (`data-loops="all"`, 보기 콤보 '이전 루프 포함') 와
  `MemoPad.swift:404-405` (`data-loops="pick"`, 지난 루프 코드 하나 고르기).
- 설계 의도가 코드 주석에 명시돼 있다 — `MemoPad.swift:44-57`. 특히 `:53-55`:
  > "대신 **이월이 자동이 아니게 됐다** — 지난 루프의 미완료를 이번 루프에서도 보려면 그 루프를
  > 열어 이번 루프로 다시 적는다. 그것이 이 설계가 사람에게 요구하는 한 가지다."

  라이언이 겪은 일은 버그가 아니라 2026-08-30 에 내려진 설계 결정의 청구서다. 그 결정의 목적은
  "새 루프 = 새 메모장" 이었고(`MemoPad.swift:44-52`), 그 대가로 손 이월을 사람에게 떠넘겼다.
  라이언이 그 대가를 못 견디겠다고 말한 것이 이번 일감이다.

**라이언에게 되물을 것 없음.** 코드로 갈렸다.

### 1-4. 지금 이 맥의 실제 상태 (2026-09-01 확인) — 이 사양이 다루는 데이터 그 자체

`~/.condition-mate/memo.json`, `~/.condition-mate/review/releases.json`,
`~/.condition-mate/review/sprints.json` 를 직접 읽어 `loopOf` 를 손으로 재현한 결과다.

- 메모 98줄. **바틀넥(`- [!]`) 7줄, 완료(`- [x]`) 6줄, 미완료(`- [ ]`) 0줄.**
- 바틀넥 7줄 = 라이언이 말한 그 줄들이다: `트위터 구매건`, `CEO`, `pre sales`,
  `MPC 지급 정리-에어드롭 말고도 빠진것이 있다.`, `jira + issue`,
  `amani event -> we need to make wraping well`, `subscription management`.
- 생성 시각은 `2026-08-30T15:00:44Z` ~ `2026-08-31T06:34:12Z`.
- 릴리즈 컷: `26-61` 이 **`2026-09-01T06:03:32Z`(KST 15:03)에 잘렸다.**
- 열린 스프린트: **`26-62` 하나** (`sprints.json`, `closed:false`). 따라서 `bgLoop.cur` = `26-62`.
- `loopOf` 를 그대로 계산하면 **바틀넥 7줄 전부가 `26-61`** 이다. 하나도 안 흩어져 있다.

**결론 셋:**

1. **지금 이 순간 라이언의 패드에서 그 7줄은 전부 안 보인다.** `rlp(26-61) !== LCUR(26-62)` 이므로
   `data-lold` 가 붙어 감춰진 상태다(`MemoPad.swift:2174-2175`, `:393`). 라이언이 화면을 보며
   말했을 때는 26-61 이 아직 열려 있었고, 그 뒤 15:03 에 잘렸다. 그가 말한 "루프에서 사라지거든"
   이 지금 실제로 일어나 있다.
2. **직전 루프 하나만 대상으로 잡는 §2-3 의 범위가 맞다.** 7줄이 전부 같은 루프(26-61)에 있으므로
   범위를 넓힐 이유가 없다. 오늘 버튼을 붙이면 라벨은 **`26-61 바틀넥 7줄 가져오기`** 가 된다.
3. **미완료(`todo`) 줄이 0개다.** §3 에서 미완료를 이월 대상에서 뺀 결정은 지금 이 데이터에서는
   아무 차이도 만들지 않는다 — 손해 없이 범위를 좁힐 수 있다는 뜻이다.

곁가지로 확인된 것 하나: `트위터 구매건`·`pre sales`·`amani event…` 는 **바틀넥 줄과 완료 줄이
제목이 같은 채로 둘 다 존재한다**(완료 쪽은 `2026-09-01T05:52` 생성, `@루프: 26-61` 스탬프).
같은 제목의 줄이 두 벌 있는 상태를 라이언은 이미 쓰고 있다 — §2-4 의 "복사(원본 유지)" 결정이
새로 만들어 내는 상황이 아니다.

## 2. 이월 사양

아래는 추천안(§5 = **B+안, 한 번 누르는 이월**) 기준의 사양이다.

### 2-1. 루프 종료를 무엇으로 감지하는가

**감지하지 않는다.** 이월은 컷 이벤트가 아니라 **사람이 누른 버튼** 이 일으킨다.

까닭: 컷은 이미 `MemoStore.harvestLoop`(`MemoStore.swift:127`) 로 메모 텍스트를 서버가 다시 쓰는
유일한 자리다. 그 쓰기 경로는 판번호 충돌 방어 + 3회 재시도(`MemoStore.swift:129-135`)로 감싸여
있고, 패드 쪽은 네 겹(판번호·포커스 새로고침·로컬 초안·저장됨 표시, `MemoPad.swift:113-127`)으로
"적었는데 사라졌다" 를 막고 있다. 이월을 그 안에 넣으면 이 앱에서 가장 위험한 쓰기를 하나 더
늘리는 일이다. 얻는 것은 "버튼 한 번" 뿐이다.

대신 **버튼이 스스로 나타난다.** 패드는 이미 컷을 즉시 안다:
`DashboardContent.completeSprintPost()` 가 컷 직후 `CMMemo.boardChanged()` 를 부르고
(`DashboardContent.swift:4291-4294`), 패드는 스로틀을 건너뛰어 보드를 다시 읽는다
(`MemoPad.swift:4120`). 그 순간 아래 버튼이 개수와 함께 켜진다.

### 2-2. 새 루프를 무엇이 만드는가

**메모패드는 루프를 만들지 않는다.** 루프는 보드가 만든다 — `ReviewStore.completeSprint()`
(`ReviewStore.swift:1411`). 패드는 `bgLoop.cur` 를 읽어 따라갈 뿐이다(`MemoPad.swift:2088`).
이 사양은 그 관계를 바꾸지 않는다.

> **알아 둘 경계 하나.** `completeSprint` 는 **미완료 보드 목표가 남아 있을 때만** 후속 스프린트를
> 만든다(`ReviewStore.swift:1440-1441`). 보드 목표를 전부 끝내고 컷하면 열린 스프린트가 없어져
> `bgLoop.cur` 가 `''` 가 되고, 그러면 `MemoPad.swift:2174` 의 `!!LCUR` 가 거짓이라 패드는
> **아무것도 감추지 않는다**. 그 상태에서는 이월할 것도 없다(다 보인다). 그래서 버튼은
> `bgLoop.cur` 가 비면 **비활성** 이다. A안(자동 이월)이었다면 이 자리에서 "이월 대상 루프가
> 없다" 는 정의되지 않은 상태를 만든다 — B+안은 이 문제를 통째로 피한다.

### 2-3. 이월할 것 — 새 UI 항목 하나

보기 콤보의 **루프 절**, 기존 `루프 종료` 버튼 바로 아래(`MemoPad.swift:2976-2983` 인접)에 항목을
하나 더한다.

- **라벨(활성):** `<출처코드> 바틀넥 N줄 가져오기` (예: `26-60 바틀넥 3줄 가져오기`). 코드를
  라벨에 박는 이유: 어느 루프에서 끌어오는지 누르기 전에 보여야 한다. 0이면 비활성 +
  `지난 루프에 바틀넥 줄이 없습니다`.
- **출처 루프를 고르는 법 — `bgLoop.prev` 를 그냥 쓰지 않는다.** `bgLoop.prev` 는 '최신 릴리즈
  코드'(`MemoPad.swift:2088`, `:33-34`)인데, 같은 스프린트의 부분 커밋이 `26-38.2` 같은 코드를
  만들 수 있어(`nextReleaseCode(forSprint:)`, `ReviewStore.swift`) 줄이 하나도 없는 코드를
  가리킬 수 있다. 대신 **`loopList(COUNT.lc)[0]`** 를 쓴다(`MemoPad.swift:1051-1059`) — 이미
  최신순이고, 현재 루프를 빼고, **줄이 실제로 있는 루프만** 남긴다. 비면 `bgLoop.prev` 로 폴백.
- **지난 루프를 열어 보는 중이면 그 루프에서 가져온다.** 출처 = `loopPick() || loopList(COUNT.lc)[0]`.
  `루프 종료` 와 달리 **잠그지 않는다** — 까닭은 `onEdit` 의 첫 줄이
  `if(loopPick()) loopSet('')` 이라(`MemoPad.swift:2427`, 주석 `:2422-2426`) 버튼이 만든 편집이
  **뷰를 자동으로 현재 루프로 되돌리기** 때문이다. 그래서 "26-61 을 펼쳐 놓고 눈으로 고른 뒤
  버튼을 누르면, 화면이 현재 루프로 돌아오며 그 줄들이 거기 들어와 있다" 가 그냥 된다.
  새 코드가 필요 없다. (`루프 종료` 를 잠그는 까닭은 그쪽이 **눈앞에 없는 줄**을 묻기 때문이고,
  이 버튼은 반대로 **눈앞에 있는 줄**을 가져오므로 같은 규칙을 쓰지 않는다.)
- **비활성 조건:** N == 0 · `bgLoop.cur` 가 빔 · 출처 루프를 못 정함. 이 셋뿐이다.
- **대상 줄:** `rows(pad)` 중 `row.dataset.st === 'block'` 이면서 `loopOf(row) === <출처코드>`
  인 줄. 화면에 보이는지(`shownRows`)와 무관하게 고른다 — 이 버튼은 "감춰진 것을 꺼내 오는"
  버튼이므로 `MemoPad.swift:2769` 의 복사 스코프 규칙을 따르지 않는다.
- **동작:** `insertItems(pad, 대상.map(...))` (`MemoPad.swift:2742`). 캐럿 자리 뒤에 붙는다.
- **되돌리기:** `insertItems` 가 `onEdit(pad, true)` 를 부르므로(`MemoPad.swift:2758`) **⌘Z 한
  단계**로 통째로 취소된다. 새 되돌리기 코드를 쓰지 않는다.
- **왜 새 줄이 즉시 안 감춰지는가 (실측 확인).** `insertItems` → `onEdit`(`:2421`) →
  `crStampNew(src)`(`:2428`, `:1205`)가 **`paint()` 보다 먼저** 새 줄에 '지금' 스탬프를 찍는다.
  그래서 `paint` 의 `loopOf`(`:1038-1046`)가 읽을 때 이미 현재 루프 소속이고 `data-lold` 가
  안 붙는다. 이 순서가 이 기능이 성립하는 근거이므로 **바꾸면 안 된다.**

### 2-4. 복사인가 이동인가

**복사다. 원본은 지난 루프에 그대로 둔다.**

세 가지 까닭:

1. 이 앱의 감춤은 전부 CSS 뿐이고 저장 텍스트를 건드리지 않는 것이 규칙이다
   (`MemoPad.swift:371`, `:379`, `:392`, `:423`). 원본을 옮기면(= 텍스트를 다시 씀) 이 규칙을 깬다.
2. 지난 루프를 열어 볼 때(`data-loops="pick"`) 그 루프의 기록이 온전해야 한다 — 이동시키면
   26-60 을 열었을 때 그때 막혀 있던 것이 사라져 있다.
3. 되돌리기가 단순해진다. 복사는 "새로 만든 줄을 지운다" 한 단계다.

**복사의 대가:** 같은 제목의 줄이 두 벌 존재한다. 지난 루프는 감춰져 있으므로 기본 화면에서는
한 벌만 보인다 — 라이언이 실제로 볼 화면은 안 바뀐다.

### 2-5. 이월된 줄이 무엇을 들고 오고 무엇을 버리는가

| 항목 | 결정 | 까닭 |
|---|---|---|
| 제목 | 그대로 | — |
| 상태 `block`(`!`) | **유지** | 아래 §2-6 |
| 상세(접힌 본문) | 그대로 | 바틀넥은 "왜 못 했는지" 가 상세에 있다(`docs/proto/memo-checklist.html:270`) |
| 칸(목표일·담당·팀·프로젝트·부모·지라·노션·슬랙) | 그대로 | 같은 일이므로 맥락을 잃을 이유가 없다 |
| `@생성` 스탬프 | **버린다 → 새로 찍는다** | 옛 스탬프를 들고 오면 `loopOf`(`MemoPad.swift:1038-1046`)가 그 줄을 **지난 루프로 판정해 즉시 다시 감춘다**. 이월이 곧바로 무효가 된다. `crStampNew`(`MemoPad.swift:1205`)가 '지금' 으로 찍게 둔다 |
| `@골: N` 골번호 | **버린다 → 새로 채번** | 번호는 불변·재사용 없음이 규칙이다(`MemoPad.swift:23`). 복사본 두 개가 같은 번호를 달면 규칙이 깨진다. 원본 번호는 §2-8 의 `@이월` 스탬프로 이어진다 |
| `@루프` 스탬프 | 애초에 없다 | `block` 줄에는 `lp` 가 붙지 않는다 — `MemoPad.swift:1761` 이 지운다 |
| 취소선(U+0336) | 그대로 따라온다 | 글자에 붙은 결합 문자다(`MemoPad.swift:2625`). 별도 처리 불필요 |

### 2-6. 이월된 줄의 `!` 표시는 유지되는가 초기화되는가

**유지한다. `block` 그대로 들어간다.**

까닭: 라이언의 `!` 는 "막혔다" 이면서 동시에 "이건 다음 루프에서 쓰겠다" 는 표시다(그의 말 그대로).
새 루프에서 `todo` 로 초기화하면 그가 스스로 붙인 판단이 지워지고, 새 루프의 미완료 목록에 섞여
"이건 막혀 있던 것" 이라는 정보가 사라진다. 그리고 원 클릭 한 번이면 언제든 내릴 수 있다
(`MemoPad.swift:1746-1752`) — 유지가 되돌리기 쉬운 쪽이다.

### 2-7. 정확한 저장 텍스트 예

이월 전 (지난 루프 26-60, 감춰져 있음):
```
- [!] jira + issue
    @골: 412
    @생성: 2026-08-30T02:14:07Z
    @담당: 라이언
    붙어 있는 이슈 링크가 깨져 있음
```
이월 후 (현재 루프 26-61 에 새로 생기는 줄):
```
- [!] jira + issue
    @골: 588
    @이월: 26-60
    @생성: 2026-09-01T11:02:33Z
    @담당: 라이언
    붙어 있는 이슈 링크가 깨져 있음
```
원본 줄은 한 글자도 안 바뀐다.

### 2-8. `@이월` 스탬프 — 새 문법 하나

`@골`·`@루프`·`@생성` 과 **정확히 같은 문법**(4칸 들여쓴 줄)을 쓴다. 값은 **최초 출처 루프 코드**.

- **재이월 시 덮어쓰지 않는다.** 26-60 → 26-61 → 26-62 로 세 번 넘어와도 값은 `26-60` 으로
  고정이다. 라이언의 질문이 "이게 몇 번째 루프에서 넘어온 항목인가" 이므로 알아야 할 것은
  **어디서 시작했나** 다. 몇 번 넘어왔는지는 `loopList`(`MemoPad.swift:1051`)가 아는 루프 목록에서
  `@이월` 값과 현재 루프 사이를 세면 나온다 — 새 상태를 저장할 필요가 없다.

> **⚠ 구현자가 반드시 지킬 함정.** `parse`(`MemoPad.swift:1560-1605`)의 마지막 갈래
> `if(f){ last.fields[f[1]]=f[2]; return; }` (`:1600`)는 **모르는 `@키` 를 전부 '칸' 으로
> 삼킨다.** 그런데 칸의 직렬화는 `fieldsOf`(`MemoPad.swift:1608-1616`)가 `.cmm-fs input` DOM
> 에서만 읽고, 그 input 은 고정 목록 `FIELDS`(`MemoPad.swift:774`)로만 만들어진다. 따라서
> `@이월` 을 그냥 두면 **파싱은 되는데 다음 저장에서 조용히 증발한다.**
> `@이월` 은 `@루프` 가 하는 것과 똑같이 세 자리를 전부 손봐야 한다:
> `parse` 전용 갈래(`:1586-1592` 본떠) → `makeRow` 의 `dataset` 슬롯(`:1724` 본떠) →
> `lineOf` 의 출력 줄(`:1677` 본떠). 세 자리 중 하나라도 빠지면 스탬프가 사라진다.

### 2-9. 화면 표시

이월된 줄에 작은 회색 꼬리표 `26-60에서 이월` 을 단다. 골번호 칩과 같은 급의 조용한 표시로,
빨강/녹색을 쓰지 않는다(앱 규칙, `MemoPad.swift:231`). 배너는 만들지 않는다(앱 규칙).

## 3. 완료된 줄(파란 체크·취소선)은 이월하지 않는 것이 맞는가

**맞다. 이월하지 않는다. 별도 처리도 필요 없다.**

`done` 줄은 이 앱에서 이미 **다른 목적지**를 가진 유일한 상태다. 컷이 일어나면
`MemoStore.harvestLoop`(`MemoStore.swift:127`)가 `- [x]` 줄만 골라 `@루프: <releaseCode>` 를 찍고,
그 제목들을 릴리즈의 `notes` 에 실어 '완료된 루프' 로그에 남긴다
(`ReviewStore.swift:1341`, `:1386`, `MemoStore.swift:113-125`). 완료 줄을 다음 루프로 가져가면
같은 일이 두 루프의 완료 로그에 중복으로 잡힌다.

취소선(`⌘⇧S`)은 상태가 아니라 글자 장식이므로(`MemoPad.swift:2625`) 판정에 쓰지 않는다.

**같이 결정해 둔 것 — 나머지 두 종류는 이월하지 않는다.**

| 줄 종류 | 이월? | 까닭 |
|---|---|---|
| `block` (`- [!]`, 주황 `!`) | **한다** | 라이언이 직접 붙인 "다음 루프에서 쓰겠다" 표시 |
| `done` (`- [x]`) | 안 한다 | 위 — 완료 로그가 이미 거둔다 |
| `todo` (`- [ ]`, 아이콘 없음) | 안 한다 | 라이언이 지목한 것은 `!` 뿐이다. 미완료까지 자동으로 끌고 오면 2026-08-30 의 "새 루프 = 새 메모장"(`MemoPad.swift:44-52`)이 무의미해지고, 패드가 영원히 안 비워진다 |
| 평문 (체크리스트 아님) | 안 한다 | 상태가 없으니 이월할 판단의 근거가 없다 |

미완료·평문이 필요하면 기존 길이 그대로 남아 있다 — 보기 콤보에서 지난 루프를 골라 보고
복사·붙여넣기(§5 참조).

## 4. 이월 이력을 어디에 남길지

**저장 텍스트 안, 그 줄 자신에게 남긴다.** `@이월: <최초 출처 루프 코드>` (§2-8).

별도 원장 파일도, 새 JSON도, 새 엔드포인트도 만들지 않는다. 까닭 셋:

1. **이 패드의 진실은 텍스트 하나다.** `@골`·`@루프`·`@생성` 이 모두 그 자리에 산다
   (`MemoPad.swift:69-75`). 이력만 다른 곳에 두면 줄을 지웠을 때 이력이 고아가 되고, 히스토리
   복원(`MemoStore.history`, `MemoStore.swift:186`)이 그 줄을 되살려도 이력은 안 따라온다.
2. **병합·판번호·히스토리 보호를 공짜로 받는다.** 텍스트에 있으면 네 겹 방어
   (`MemoPad.swift:113-127`)가 그대로 걸린다. 밖에 두면 그 보호가 없다.
3. **다른 편집기로 열어도 읽힌다.** 저장 포맷이 마크다운스러운 평문이라는 약속을 지킨다
   (`MemoPad.swift:76-77`).

**라이언이 실제로 보는 것:**
- 줄 옆 꼬리표 `26-60에서 이월` (§2-9)
- CSV 내보내기(`toCSV`, `MemoPad.swift:2639`)에 `이월` 열을 하나 더한다 — 표로 빼면 "몇 개가
  몇 루프째 끌려오고 있나" 가 정렬 한 번에 보인다. 가져오기(`fromCSV`, `:2694`)도 이름으로 열을
  찾으므로 왕복이 유지된다.
- "몇 번째 루프에서 넘어왔나" 는 저장하지 않고 `@이월` 값과 `loopList`(`MemoPad.swift:1051`)로
  계산한다.

## 5. A안 vs B안 — 추천은 **B+안** 하나다

### 먼저: B안의 절반이 아니라 **전부** 가 이미 있다

라이언이 "복사·붙여넣기 경로가 이미 절반 있는 것인지" 물었다. 확인한 결과 **왕복이 이미 통째로
동작한다.** 라이언이 모르고 있었을 뿐이다.

| 단계 | 코드 | 상태 |
|---|---|---|
| 복사 — 우클릭 → `메모 그대로 복사` → `list.map(lineOf).join('\n')` | `MemoPad.swift:3640` | `lineOf`(`:1672`)가 `- [!] 제목` 을 그대로 내보낸다 |
| 붙여넣기 — 여러 줄 평문은 `parse(txt)` 로 행을 세운다 | `MemoPad.swift:3925-3931` | `parse`(`:1603-1604`)가 `- [!]` → `st='block'` 복원 |
| 옛 `@생성` 이 따라오는가 | `MemoPad.swift:3927` — 붙여넣기가 만드는 객체는 `{st, text, detail, fields}` 뿐, `cno`·`gno` 를 **안 싣는다** | 옛 생성 시각이 버려져 새 줄이 **현재 루프에 속한다**. 즉 붙이면 안 감춰진다 |

**그러니 `!` 표시는 클립보드에 실려 나가고, 붙여넣으면 복원된다.** 단, `메모 그대로 복사` 로
복사했을 때만이다 — 기본 ⌘C 는 `toPlain` 이라 상태 토큰을 뗀다(`MemoPad.swift:2843`).

> **실측 확인 (2026-09-01, `lion-condition-mate-worker-qa`).** 위 표는 정적 읽기가 아니라
> **실제로 굴려서** 확인했다. 수정하지 않은 shipping `MemoPad.swift` 를 Chromium 에 mount 하고
> 진짜 우클릭 → 진짜 `navigator.clipboard.writeText` → 진짜 OS 클립보드 → 진짜 `Cmd+V` →
> 패드의 진짜 `paste` DOM 핸들러까지 태웠다. `parse`/`lineOf`/`makeRow` 를 흉내 내지 않았다.
> **14개 단언 전부 통과, `swift build` 통과.** 확인된 것:
> - 붙여넣은 `- [!] …` 이 진짜 `data-st=block` 행이 된다
> - 클립보드에 실린 옛 `@생성: 2026-08-29T06:09Z` 가 **버려지고** 새 스탬프
>   `2026-09-01T06:09:39Z` 가 찍혀, 그 줄이 **감춰지지 않는다**(`vis=0111`)
> - 옛 `@골: 5` 도 버려진다(`gno:null`)
> - 복사 범위가 실제 `display` 기준이라, 지난 루프를 고르기 전에는 그 줄이 복사되지 않는다
>   (`vis=011` → 26-46 선택 후 `vis=101`)
>
> 즉 §5 의 "이미 된다" 는 추정이 아니라 관측이다.

**그런데 지금 라이언의 손은 7번 간다:**
1. 보기 콤보 열기 → 2. 지난 루프 코드 고르기 → 3. `미완료` 끄기 → 4. `완료` 끄기
(`MemoPad.swift:410-412` 로 pick 모드에서도 상태 필터가 걸린다) → 5. 우클릭 →
6. `메모 그대로 복사` → 7. 패드 클릭 후 ⌘V.
(처음에 8번으로 셌다가 7번으로 고쳤다 — '현재 루프로 복귀' 단계는 필요 없다. `onEdit` 이
붙여넣기를 편집으로 보고 뷰를 자동으로 되돌린다, `MemoPad.swift:2427`.)

게다가 3~4를 빼먹으면 완료 줄까지 딸려 온다(복사 범위 = 화면에 보이는 것, `MemoPad.swift:2769`,
`:3630`). 이 7단계를 라이언이 매 루프 한다는 것이 이 일감의 실질이다.

**따라서 이 일은 기능 추가가 아니라 이미 되는 경로를 한 번으로 줄이는 일이다.**

| 서버가 memo.json 을 다시 쓰는가 | **그렇다** (컷 안에서) | 아니다 | 아니다 |
| 되돌리기 | 어렵다 — 디스크에 박힌다. 코드 자신이 이 위험을 경고한다(`MemoPad.swift:970-974`: "사람이 수백 줄에서 손으로 찾아 지워야 낫는다") | ⌘Z | **⌘Z 한 단계** (`MemoPad.swift:2758`) |
| 미해결 경계 | 보드 목표를 다 끝내고 컷하면 후속 스프린트가 없어(`ReviewStore.swift:1440`) 이월 목적지가 정의되지 않음 | 없음 | 없음 — 그때는 버튼이 비활성 (§2-2) |
| 컷 시각 경합 | **있다. 그리고 이 사고는 이미 한 번 났다.** 이월 줄의 `@생성` 이 컷의 `releasedAt` 보다 확실히 뒤여야 새 루프에 속한다. 2026-08-30 에 스탬프(분)와 컷(초)의 눈금이 달라 컷 직후 1분 동안 "적으면 사라지는 패드" 가 됐다 — `MemoPad.swift:1078-1084`, 전용 회귀 시험 `.e2e/memocutwrite.test.js:4-12`. A안은 서버가 컷 **안에서** 스탬프를 찍으므로 이 경계에 정확히 다시 선다 | 없다 | 없다 — 붙여넣는 순간이 언제나 컷 뒤다 |
| 회귀 위험 | 높다 | 없다 | 낮다 |

### 추천: **B+안 — "지난 루프 바틀넥 N줄 가져오기" 버튼 하나**

근거를 순서대로:

1. **위험 대비 이득이 A안에 없다.** A안이 B+안보다 나은 것은 오직 "손이 1번에서 0번" 하나다.
   루프당 클릭 한 번을 아끼려고, 이 앱에서 가장 방어가 두꺼운 쓰기 경로(`memo.json` 을 컷 안에서
   서버가 다시 쓰는 자리)에 새 로직을 넣는다. 남는 장사가 아니다.
2. **A안은 이미 내려진 설계 결정을 반쯤 되돌린다.** 2026-08-30 에 "새 루프 = 새 메모장" 으로
   정했고(`MemoPad.swift:44-52`), 그 전의 문제는 정확히 **패드가 안 비워지는 것** 이었다. `!` 를
   전부 자동으로 끌고 오면 6루프째 막혀 있는 줄이 영원히 복제되고, 고쳤던 것이 되돌아온다.
   버튼은 라이언의 판단을 한 번 거치게 한다 — 그가 목록을 보고 가져올지 정한다.
3. **되돌릴 수 있다.** ⌘Z 한 번. A안은 디스크에 박힌 뒤라 손으로 지워야 한다.
4. **가장 적게 건드린다.** 파일 1개, 기존 함수 재사용(`insertItems`·`loopOf`·`parse`·`lineOf`),
   새 엔드포인트 0개, 새 저장 파일 0개.
5. **경계가 하나도 안 열린다.** A안이 열어 두는 "후속 스프린트가 없는 컷" 과 "컷 시각 경합" 두
   구멍이 B+안에는 아예 존재하지 않는다.
6. **라이언 본인이 이쪽을 "아주 간단한 법" 이라고 불렀다.** 그의 감각이 맞았다. 다만 그가 몰랐던
   것은 이미 되고 있다는 것이고, 그래서 할 일이 "만들기" 가 아니라 "한 번으로 줄이기" 다.

### B+안이 명시적으로 하지 **않는** 것

- 보드에서 `Complete loop` 를 누르고 패드를 안 열면 아무 일도 안 일어난다. 라이언이 눌러야 한다.
- 미완료(`todo`)·평문 줄은 안 가져온다 (§3).
- 지난 **두 루프 전** 이상은 안 가져온다 — 대상은 `bgLoop.prev` 하나뿐이다. 더 옛날 것은 기존
  '지난 루프 하나 보기' + 복붙 경로가 그대로 있다.
- 서버·`memo.json` 쓰기 경로·릴리즈 컷 코드를 한 줄도 안 건드린다.

> 문서에 세우는 일이다(지금은 그 계약이 테스트 주석에만 산다).

**편집 2 — 새 절 `## P9. 대시보드 메모패드`, 항목 5개 (신규, old→new 없음)**

- **MEMO-1 — 체크리스트 3상태.** 원 클릭은 미완료 → 완료 → 바틀넥 순으로 돈다. 저장 토큰은 각각
  `- [ ] `, `- [x] `, `- [!] `. 바틀넥 마크는 `!` 이고 색은 호박색이다(빨강·녹색 금지).
  근거: `MemoPad.swift:656-657`, `:231`.
- **MEMO-2 — 루프는 보드 스프린트 코드다.** 패드의 루프 단위는 보드의 열린 스프린트 코드
  (`bgLoop.cur`)이며, `docs/loop-definition.md` 의 L1~L9 위임 파이프라인과 **무관하다**. 헤더
  `보기 <코드> (N)` 의 `<코드>` 는 현재 루프 코드, `(N)` 은 보이는 상태 축의 개수다(줄 수가 아니다).
  근거: `MemoPad.swift:2088`, `:1132-1134`, `:617`, `:898`.
- **MEMO-3 — 지난 루프 줄은 감출 뿐 지우지 않는다.** 줄이 속한 루프가 현재 루프와 다르면
  `data-lold` 가 붙어 CSS `display:none` 으로 감춰진다. 상태를 가리지 않는다(바틀넥도 감춰진다).
  **저장 텍스트는 한 글자도 바뀌지 않는다.** '이전 루프 포함' 또는 루프 코드 선택으로 언제든 다시
  보인다. 근거: `MemoPad.swift:2174-2175`, `:393-394`, `:404-405`.
- **MEMO-4 — 복사·붙여넣기는 상태를 왕복시킨다.** 우클릭 `메모 그대로 복사` 는 `- [!] ` 토큰을
  포함해 내보내고(복사 범위는 화면에 보이는 줄뿐이다), 여러 줄 평문 붙여넣기는 그 토큰을 바틀넥
  상태로 복원한다. 붙여넣은 줄은 옛 `@생성`·`@골` 을 이어받지 **않으므로** 현재 루프에 속하고
  즉시 감춰지지 않는다. `crStampNew` 가 `paint` 보다 먼저 도는 순서가 이 계약의 근거다.
  근거: `MemoPad.swift:3640`, `:3925-3931`, `:1603-1604`, `:2742-2748`, `:2421-2428`, `:1205`.
  (2026-09-01 실제 Chromium 왕복으로 검증됨)
- **MEMO-5 — (신규 기능) 지난 루프 바틀넥 가져오기.** 보기 콤보 루프 절의 버튼은 직전 루프
  (`loopList()[0]`, 줄이 실제로 있는 가장 최근 과거 루프)의 `block` 줄만 현재 루프로 **복사**한다.
  버튼 라벨은 그 출처 코드와 개수를 그대로 보여 준다. 지난 루프를 열어 보는 중이면 **그 루프**가
  출처가 되고, 누른 뒤 뷰는 `onEdit` 이 현재 루프로 되돌린다(`MemoPad.swift:2427`). 원본은 그대로 남는다. 복사된 줄은
  `block` 상태·상세·칸을 유지하고, `@생성`·`@골` 은 새로 받으며, `@이월: <최초 출처 루프 코드>`
  를 단다(재이월해도 덮어쓰지 않는다). ⌘Z 한 단계로 되돌아간다. 대상이 0개이거나
  `bgLoop.cur` 가 비면 비활성이다. 완료·미완료·평문 줄은 대상이 아니다.

## 열린 질문 (구현을 막지 않음 — 기본값은 정해 뒀다)

1. **미완료(`todo`) 줄도 같이 가져올까?** 기본값 **아니오** (§3). 라이언이 지목한 것은 `!` 뿐이고,
   미완료까지 끌면 "새 루프 = 새 메모장" 이 무너진다. 라이언이 원하면 같은 버튼에 축을 하나
   더하는 것은 나중에 몇 줄이면 된다.
2. **버튼 자리를 보기 콤보 안에 둘까, 우클릭 메뉴에도 둘까?** 기본값 **보기 콤보 루프 절 하나만**.
   기존 `루프 종료` 와 나란히 두는 것이 발견 가능성이 제일 높고, 표면을 두 곳으로 늘리지 않는다.
