# goal-28: 목표 자동 실행 루프 (backlog 큐 구동)

- 상태: backlog (다음 착수 후보 — 토대는 완료, 구동 주체만 남음)
- 목적: 대기(backlog) 상태의 goal을 자동으로 집어 실행으로 전환하는 루프를 안전하게 돌린다. 중지·취소된 goal은 루프가 절대 건드리지 않는다.
- 작성일: 2026-06-24
- 선행 설계: .claude/doc/loop-status-design.md
- 관련 정책: .claude/doc/waiting-signal-policy.md, .claude/doc/session-lifecycle-policy.md
- 관련 코드: ReviewStore(상태/전이), AppDelegate(loopQueueJSON, 세션 라우팅), DashboardServer(/api/loop/queue), DashboardContent(상태 콤보박스·필터)

## 요약

여러 에이전트를 동시에 굴릴 때 "무엇을 자동으로 집어가도 되는지"를 상태값으로 구분하고, 대기 상태만 루프가 처리하도록 만드는 작업이다. 상태 모델과 조회 API까지는 이미 구현·검증을 마쳤다. 남은 것은 실제로 큐를 읽어 실행으로 전환하는 루프 구동 주체와, 그 주체가 지켜야 할 동시 실행 한도 및 공백 구간 회수 안전망이다.

## 1. 배경 / 문제 정의

기존 goal 상태는 backlog, in_progress, done 세 개뿐이었다. 이 셋만으로는 자동 루프를 안전하게 돌릴 수 없었다. 이유는 세 가지다.

첫째, 사람의 의사결정을 기다리는 중인지 구분이 안 됐다. 여러 에이전트가 동시에 진행될 때 어떤 것이 멈춰서 사용자 응답을 기다리는지 in_progress 하나로는 알 수 없었다.

둘째, "잠시 중지"와 "취소"와 "아직 시작 안 함"이 모두 backlog 한 칸에 섞였다. 루프가 backlog를 집어가도록 만들면 사용자가 의도적으로 멈춰둔 항목이나 폐기한 항목까지 다시 끌려 들어간다.

셋째, 루프 입장에서 "집어가도 되는 것"의 정의가 모호했다. 자동 실행을 안전하게 하려면 집어가도 되는 상태와 절대 건드리면 안 되는 상태가 명시적으로 갈려 있어야 한다.

## 2. 선행 완료 (이번 작업으로 끝난 토대)

루프를 붙이기 위한 상태 모델과 조회 API는 이미 구현되어 동작 검증까지 마쳤다.

상태 모델은 여섯 개로 확정됐다. backlog(대기)는 루프가 집어가는 유일한 상태다. in_progress(진행)는 실제 작업 중이다. waiting(응답 대기)은 사람의 결정을 기다리며 멈춘 상태로, 자동 감지(Notification 훅과 transcript 풀 감지)가 이미 붙어 있다. stopped(중지)는 사용자가 잠시 보류한 상태로 루프가 건너뛴다. cancelled(취소)는 폐기 상태로 루프가 영구히 무시한다. done(완료)은 종착 상태다.

stopped와 cancelled는 사용자 권한이 우선한다. ReviewStore의 recordSession에 보호 가드를 넣어, 상태가 stopped 또는 cancelled인 goal은 세션 훅이 라벨과 transcript만 갱신하고 status나 누적 시간은 절대 건드리지 않게 했다. 이로써 보류·폐기한 goal을 세션 이벤트가 다시 큐로 끌어오는 일이 없다.

되돌리기는 모두 유지로 정했다. cancelled나 stopped에서 backlog로 복귀할 때 누적 시간과 세션 연결을 그대로 보존한다.

대시보드는 leaf goal의 상태 위젯을 여섯 상태를 담은 콤보박스로 교체했고, 필터에 취소 토글을 더해 cancelled는 기본 숨김, stopped는 항상 표시로 두었다.

조회 API로 GET /api/loop/queue를 추가했다. 응답은 backlog인 leaf goal만 seq 순으로 담은 worklist이며, in_progress, waiting, stopped, cancelled, done과 부모 goal은 모두 제외된다.

## 3. 루프 동작 정의

루프가 지켜야 할 적격성 규칙은 한 문장으로 요약된다. 루프는 오직 backlog만 집어가고, stopped와 cancelled는 절대 집어가지 않으며, waiting은 사람에게 넘긴다.

상태별로 정리하면 다음과 같다.

- backlog: 루프가 집어가는 유일한 상태. 동시 실행 한도 안에서 in_progress로 전환하고 작업을 시작한다.
- in_progress: 이미 실행 중이므로 건너뛴다. 중복 실행 금지.
- waiting: 루프가 자동으로 재개하지 않는다. 사람의 결정이 선행되어야 하므로 화면에 부각만 하고 큐로는 넣지 않는다.
- stopped: 의도적 보류. 사용자가 재개하기 전까지 건너뛴다.
- cancelled: 폐기. 영구적으로 건너뛴다.
- done: 종착. 건너뛴다.

루프가 한 항목을 처리하는 흐름은 이렇다. 큐에서 항목을 집어 in_progress로 바꾸고 작업을 진행한 뒤, 완료면 done, 사용자 응답이 필요하면 waiting(보통 세션 훅이 자동 처리), 보류면 stopped, 폐기면 cancelled로 전이시킨다.

## 4. 설계 선택지 — 구동 주체

루프 자체는 두 가지 방식이 가능하다. 이번 토대는 두 방식 모두를 지원하도록 상태와 API 중심으로 만들어 두었다.

- 외부 폴링 방식: 외부 실행기(예: Claude Code 루프)가 GET /api/loop/queue를 주기적으로 읽어, 동시 실행 한도 안에서 항목을 집어 실행한다. 앱은 상태 원장과 큐 제공자 역할만 한다. 합의된 1차 방향이다.
- 앱 내부 스캐너 방식: 앱 안에 주기 스캐너를 두어 backlog를 직접 집어 in_progress로 전환한다. 외부 에이전트 실행 연결은 추후 과제다.

어느 쪽이든 3절의 적격성 규칙과 아래 5절의 안전 장치는 동일하게 적용한다.

## 5. 구현해야 할 것

루프 구동 주체를 붙일 때 함께 구현해야 하는 보호 장치는 다음과 같다.

동시 실행 한도를 지켜야 한다. 무한정 항목을 띄우지 않도록 동시에 in_progress로 둘 수 있는 개수에 상한을 둔다. 현재 대시보드는 active parent(롤업이 on_track인 부모) 개수로 에너지·에이전트 입력을 게이팅하고 있으므로, 루프도 같은 기준과 정합되게 한도를 참조한다.

공백 구간의 유예-회수 안전망을 둔다. 루프가 backlog를 in_progress로 바꿨는데 일정 시간 안에 실제 에이전트(세션)가 붙지 않으면 backlog로 되돌린다. 표시상으로만 진행이고 실제로는 아무도 일하지 않는 좀비 항목을 방지하기 위함이다. 기존 detectWaitingSessions의 transcript 기반 풀 감지와 같은 결의 보호 장치다.

우선순위를 존중한다. 큐는 seq 순으로 정렬되어 제공되므로, 루프는 앞에서부터 집어 사용자가 정한 우선순위를 따른다.

## 6. 미결정 / 리스크

구동 주체를 외부 폴링으로 갈 경우, 폴링 주기와 한도를 어디에 둘지(외부 설정 대 앱 설정) 정해야 한다.

유예-회수의 임계 시간을 얼마로 둘지, 그리고 회수가 반복되는 항목(계속 in_progress로 갔다가 회수되는 항목)을 어떻게 표시하거나 보류시킬지 정해야 한다.

여러 외부 실행기가 동시에 같은 큐를 읽을 때의 경합이다. 두 실행기가 같은 backlog 항목을 동시에 집을 수 있으므로, in_progress 전환을 선점(claim)으로 다루는 방식이 필요할 수 있다. 현재 API는 단순 조회만 제공하므로, 필요 시 원자적 claim 엔드포인트를 추가하는 것을 검토한다.

## 7. 수용 기준

- 루프가 backlog leaf goal만 집어 실행으로 전환하고, stopped·cancelled·waiting·done·부모 goal은 절대 집지 않는다.
- 동시 실행이 정해진 한도를 넘지 않는다.
- in_progress로 전환된 뒤 정해진 유예 안에 세션이 붙지 않으면 backlog로 회수된다.
- 사용자가 중지·취소한 항목은 세션 이벤트가 와도, 루프가 돌아도 상태가 유지된다(선행 완료 항목으로 이미 검증됨).
- 큐 처리 순서가 seq 우선순위를 따른다.
