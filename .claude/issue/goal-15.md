# goal-15: 목표의 날짜별 관리

- 상태: backlog (보류 결정 — 지금은 착수하지 않음)
- 결정: 현 시점에는 구현하지 않는다. 본 문서는 목표 정의와 보류 사유를 기록한다.
- 목적: 목표(goal)를 "오늘 할 일" 관점이 아니라 날짜 축으로 누적/조회 관리
- 작성일: 2026-06-24
- goal id: 0855994D-A317-4D1D-8F02-C0548D72A5ED ("날짜관리")
- 관련 코드: ReviewStore, review/goals.json, DashboardContent, DashboardServer

## 결정 요약

목표를 날짜별로 관리하는 기능은 **지금은 하지 않는다.** 이유는 아래 4절에
정리한다. 핵심은, 현재 목표 모델이 아직 안정화 중이고(고정 id·tier 평활·온트랙
롤업이 막 들어옴) 데이터 영속 구조도 방금 `.localdata`로 옮겨 정리한 직후라,
날짜 차원을 지금 끼워 넣으면 모델이 두 번 흔들린다는 점이다. 먼저 현재 모델을
며칠 굴려보고, 날짜 관리가 실제로 필요한 사용 패턴이 확인되면 그때 착수한다.

## 1. 배경 / 문제 정의

현재 목표는 단일 리스트(`review/goals.json`)에 status(backlog / in_progress /
done)만 가진 평면 구조다. "언제의 목표인가"라는 시간 축이 없다.

이로 인해 생기는 한계:

- 오늘 한 일과 어제 한 일이 같은 리스트에 섞인다. done 처리한 목표가 계속
  목록에 남아 누적되면 "오늘 관점"이 흐려진다.
- 날짜별 회고(특정 날짜에 어떤 목표를 잡았고 얼마나 추적했는가)가 불가능하다.
- 활동 로그(activity-YYYY-MM-DD.jsonl)와 통계(stats.perDay)는 이미 날짜축으로
  쌓이는데, 목표만 날짜축이 없어 "그날의 목표 ↔ 그날의 활동"을 엮을 수 없다.

즉 데이터의 다른 축(활동/통계)은 날짜로 정렬돼 있는데 목표만 평면이라,
회고·대시보드에서 비대칭이 생긴다.

## 2. 현재 구조 요약

- ReviewStore (Core/ReviewStore.swift): 목표 CRUD와 `review/goals.json` 영속화.
  각 목표는 고정 id(UUID), text, status, trackedSeconds 등을 가진다. 날짜 필드 없음.
- review/goals.json: 목표 배열. 날짜 그룹핑 개념 없이 전체가 한 리스트.
- DashboardContent / DashboardServer: 현재 목표 리스트를 그대로 렌더. tier 평활,
  온트랙 롤업은 "현재 시점" 기준으로 계산.
- activity / stats: 날짜별로 분리 저장(파일명·perDay 키). 목표와 정반대로
  이미 날짜축이 1급 시민.

빠진 것은 목표에 "어느 날짜에 속하는가" 또는 "어느 날짜에 활성이었는가"라는
시간 차원과, 그걸 조회·롤오버하는 로직이다.

## 3. 만든다면 — 설계 선택지 (지금 결정하지 않음, 메모만)

날짜 관리는 의미가 갈리므로, 착수 시 먼저 정의를 못박아야 한다.

- 해석 A — "그날 생성된 목표": 목표에 createdDate를 박고 날짜별로 묶어 본다.
  단순하지만, 여러 날에 걸친 장기 목표를 어느 날에 둘지 모호하다.
- 해석 B — "그날 활성/추적된 목표": 목표는 지속되되, 날짜별 활성 여부·추적시간을
  별도 인덱스로 쌓는다(목표 × 날짜 매트릭스). 활동 로그와 자연스럽게 엮이지만
  영속 구조가 한 단계 복잡해진다.
- 해석 C — "데일리 롤오버": 매일 자정에 미완료 목표를 다음 날로 넘기고 done은
  과거로 봉인. 할 일 관리(TODO) 패러다임. 회고보다 운영에 가깝다.

추가 고려:
- trackedSeconds를 전체 누적이 아니라 날짜별로 쪼갤 것인가(해석 B의 핵심 비용).
- 자정 경계 처리(activity 로그가 이미 로컬 자정 기준으로 파일을 가르는 방식과 정합).
- 마이그레이션: 기존 평면 goals.json을 날짜 모델로 옮길 때 과거 목표의 날짜를
  무엇으로 채울지(생성 시각 정보가 현재 없음 → 소급 불가 가능성).

## 4. 지금 보류하는 이유

- 모델이 흔들리는 시점이다. 직전 작업으로 목표에 고정 id, tier 평활, 온트랙
  롤업이 막 들어왔다. 여기에 날짜 축까지 동시에 얹으면 한 릴리스에서 목표
  모델이 두 번 깨진다. 한 번에 하나씩 안정화하는 편이 안전하다.
- 영속 구조를 방금 정리했다. 데이터 위치를 `.localdata`로 옮기고 단일 소스로
  맞춘 직후다. 스키마를 또 건드리면 마이그레이션 리스크가 겹친다.
- 정의가 아직 안 섰다. 3절의 해석 A/B/C는 사용자 경험이 완전히 다르다. 어떤
  것을 원하는지는 현재 평면 모델을 며칠 써보고 "무엇이 불편한지"가 드러나야
  정할 수 있다. 지금 정하면 추측 기반 설계가 된다.
- 우선순위. 진행 중인 모티베이션/가치 파이프라인 작업이 사용자 가치에 더
  직접적이다. 날짜 관리는 회고 편의 기능으로, 급하지 않다.

## 5. 재검토 트리거 (이때 다시 연다)

- 현재 평면 목표 리스트에서 done 누적으로 "오늘 관점"이 실제로 불편해질 때
- 날짜별 회고(그날의 목표 ↔ 그날의 활동/통계 대조)를 실제로 보고 싶어질 때
- 목표 모델(id/tier/온트랙)이 며칠 운영으로 안정화된 뒤

재검토 시 첫 결정사항: 3절의 해석 A/B/C 중 무엇인지부터 못박고 시작한다.
