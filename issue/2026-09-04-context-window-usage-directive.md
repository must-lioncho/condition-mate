## 지금 화면에 있는 것과 없는 것

토큰 뷰의 세션 행 보조 줄은 이렇게 나온다.

```
컨 77(재 71·결 5·타 0.4·사 0)·생 0·응 4·도 19% · opus-5 HIGH 100% · AI 61분 · 리드 3.7분·9회
```

여기서 `컨 77%` 는 **구성비**다. 그 세션이 쓴 토큰 총합 중 프롬프트 쪽이 77% 라는 뜻이지,
창을 77% 채웠다는 뜻이 아니다. 라이언이 묻는 것은 후자이고, 그 값은 지금 화면에 없다.

없는 이유는 데이터가 없어서가 아니라 **집계 축이 다르기 때문**이다. 지금 파이프라인은
`spent = input + output + cache_creation` 을 메시지마다 더해 하루치로 접는다
(`AppDelegate.swift:4826` 부근 fold 루프). 이 값은 **창을 몇 번 채웠는지**를 재는 축이고,
**창을 얼마나 채웠는지**를 재는 축이 아니다. 창 점유는 더하면 안 되는 값이다.

## 갈래 하나 — "최종적으로 몇 퍼센트" 의 분자와 분모

### 결정

- **분모 = 그 세션이 실제로 쓴 모델의 컨텍스트 윈도우(토큰).**
- **분자 = 한 어시스턴트 요청에 실제로 실린 프롬프트 총량**
  = `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`.
- **측정 지점 = 그 세션·그날의 마지막(비-sidechain) 어시스턴트 메시지.** 이것이 "최종".
  같은 순회에서 최대값(피크)도 같이 잡는다.
- **누적 `spent` 를 분자로 쓰지 않는다.**

### 왜 이렇게 정했나 — 디스크를 세어 보고 정했다

`~/.claude/projects` 아래 트랜스크립트를 훑어 메시지마다
`input + cache_read + cache_creation` 을 계산했다.

- 관측된 최대 컨텍스트: 823,490 토큰 (`claude-opus-5`, 세션 `53c8820a`).
- 누적 토큰(`spent`)은 이 축이 아니다. 창을 몇 번 채웠는지지 얼마나 채웠는지가 아니다.

**최종과 피크는 둘 다 저장하고, 다르면 둘 다 보인다.** 이유 셋이다.
(1) 라이언이 "최종" 이라고 말했으므로 주 값은 최종이어야 한다.
(2) 이 화면의 행은 세션이 아니라 **세션×날짜**다. 이틀에 걸친 세션의 첫날 행은
    "그날의 최종" 이고 세션 전체의 피크와 갈릴 수 있다.
(3) 세션 안에서 컨텍스트가 실제로 줄어드는 경우가 있다.

### 정정 — 이 지시서의 초판이 틀렸다 (2026-09-04, 구현 중 잡힘)

초판은 이 자리에 "최근 20일 400 개 표본에서 마지막 값 ÷ 최대값이 전부 1.00 이므로
종료 시점과 최고점은 같은 값" 이라고 적었다. **틀렸다.** 400 개는 전수가 아니었고,
그 표본에 반례가 우연히 없었을 뿐이다.

전수(1,739 세션)로 다시 세었다:

- **22 개 세션에서 최종 ≠ 피크다** (1.3%). 컨텍스트가 세션 도중 실제로 줄어든다.
- 예: `cb865437` (`claude-fable-5`) — 피크 409,470 인데 최종 117,301.
  화면에는 `창 1M · 11.7%(최대 41%)` 로 나온다.
- 예: `6e696696` (`claude-opus-5`) — 최종 313,393 / 피크 343,949.

그러므로 "둘 다 저장한다" 는 결정은 보험이 아니라 **필수**였다. 최종만 남겼으면
409K 를 쓴 세션이 117K 짜리로 보여서 라우팅 판단을 정확히 반대로 만들었을 것이다.
결정은 그대로 두고 근거만 바꾼다 — 결정이 우연히 맞았던 것을 근거가 맞았던 것으로
적지 않기 위해 이 절을 남긴다.

### sidechain 을 세지 않는다

서브에이전트(`isSidechain: true`) 줄은 **자기 컨텍스트를 따로 갖는다.** 그것을 부모
세션의 창 점유로 세면 부모가 쓰지도 않은 창을 쓴 것으로 보인다. 창 점유 계산에서만
sidechain 을 제외한다 — 토큰 합계·비용은 지금대로 sidechain 을 포함한다(그것은 실제로
나간 돈이므로 축이 다르다).

## 갈래 둘 — 모델별 윈도우 크기 표를 어디서 가져오는가

### 결정

**Swift 쪽(`AppDelegate.swift`)에 상수 표를 두고, 서버가 퍼센트까지 계산해 내려준다.**
클라이언트(`DashboardContent.swift`)는 받은 값을 그리기만 한다.

### 왜 Swift 인가 — 단가 표(`TK_PRICE`)는 JS 에 있는데

단가는 클라이언트가 이미 가진 `models` 맵만으로 계산된다. **창 점유는 아니다.** 점유를
클라이언트에서 계산하려면 턴별 컨텍스트 배열을 전부 내려보내야 하고, 일 행 하나에 세션이
62 개인 날이 있으므로 `/tokens.json` 이 그만큼 무거워진다. 서버는 이미 그 파일들을 순회
중이므로 거기서 계산하면 추가 비용이 0 이다.

### 표는 시작값일 뿐이고, 관측이 표를 이긴다

opus-5 의 공시 기본 창은 200K 인데 디스크에는 823K 짜리 세션이 있다. 1M 컨텍스트 베타로
띄운 창이다. 그러므로 **표만 믿으면 점유율이 400% 로 나온다.**

규칙:

```
창 = 표에 있는 기본값
관측 피크 > 창 이면 → 관측 피크를 담는 가장 작은 공시 단계로 올린다 (단계: 200K, 1M)
표에 없는 모델 → 창 = null → 화면에 "창 —" (숫자를 지어내지 않는다)
```

이 규칙은 **위로만 자기교정된다.** 표가 낮게 틀렸으면 관측이 고치고, 표가 높게 틀렸으면
점유율이 실제보다 낮게 보인다. 후자는 "창이 남았다" 는 낙관이므로 라우팅을 보수적으로
만들지 않는다는 한계가 있다 — 이것은 알고 받아들이는 것이며, 표 값을 갱신하는 것 말고
자동으로 고칠 방법이 없다.

### 표 (2026-09-04 시점 공시 기준. 근거 날짜를 주석으로 같이 적을 것)

| 모델 접두어 | 기본 창 |
|---|---|
| `claude-opus` | 200_000 |
| `claude-fable` | 200_000 |
| `claude-mythos` | 200_000 |
| `claude-sonnet` | 200_000 |
| `claude-haiku` / `claude-3-5-haiku` / `claude-3-haiku` | 200_000 |
| `gemini-` | 1_048_576 |
| `gpt-4o` | 128_000 |
| `o1` / `o3` | 200_000 |
| 그 밖 (`glm-*` 포함) | null → "창 —" |

`glm-*` 을 비워 두는 것은 지금 z.ai 공시 창 크기를 확인하지 못했기 때문이다. **모르는 것을
채워 넣지 않는다.** GLM 세션은 관측 피크만 보이고 점유율 자리는 `—` 가 된다.

### 턴별 데이터가 없는 provider

Codex·Antigravity 수집기는 세션 총 토큰만 준다. 그 행은 `ctxFinal`/`ctxPeak` 를 `null` 로
두고 점유율을 그리지 않는다. 0% 로 그리면 "창이 텅 비었다" 는 거짓말이 된다.

## 형식 — 원문에 없으므로 여기서 정한다

라우팅 판단은 세션 하나를 뜯어보는 일이 아니라 **어느 세션이 큰 창을 실제로 필요로 했는지
훑는 일**이다. 그래서 값은 세션 행에 붙이고, 색으로 훑을 수 있게 한다.

1. **세션 행 보조 줄 맨 앞에 칩 하나를 붙인다.**
   `창 1M · 62%` — 지금의 `컨 77(재 …` 앞이다.
   최종과 피크가 다르면 `창 1M · 62%(최대 71%)`.
   창을 모르면 `창 — · 388K`(점유율 대신 절대 토큰).
   툴팁: 모델 이름, 창 크기, 최종 컨텍스트 토큰 수, 피크 토큰 수, 그리고 한 줄 산식
   `input + cache_read + cache_creation (마지막 어시스턴트 요청, 서브에이전트 제외)`.
2. **색**: 80% 이상 `#e5534b`, 50–80% `#d29922`, 50% 미만은 `.muted` 그대로.
   라우팅 결론이 색 하나로 끝나야 한다 — 빨강은 "이 창이 아니면 안 됐다", 회색은
   "더 작은 모델로 됐다".
3. **일(日) 그룹 줄과 기간 요약 줄**에 분포를 한 조각 추가한다:
   `창 점유 중앙 41% · 80%↑ 3개`. 세션 하나가 아니라 분포를 봐야 라우팅을 바꾼다.
   세션 수가 0 이거나 창을 아는 세션이 하나도 없으면 이 조각을 통째로 뺀다.
4. **범례**(`DashboardContent.swift:859` 의 `일별 토큰 사용량` 설명 문단)에 두 문장 추가.
   `창`이 무엇이고 `%`가 무엇으로 나눈 것인지, 그리고 1M 승격 규칙이 있다는 것.

### 이번에 하지 않는 것

- 창 점유로 정렬하거나 거르는 기능. (칩이 먼저 붙고 나서 필요하면 그때)
- 모델 추천("이 세션은 sonnet 으로 됐다") 문구 자동 생성. 판단은 라이언이 한다.
- 단가 표(`TK_PRICE`)를 Swift 로 옮기는 일. 축이 다르고, 건드리면 비용 숫자가 흔들린다.
- Codex·Antigravity 수집기에 턴별 컨텍스트를 새로 파게 하는 일.

## QA 가 되물은 두 가지 — 여기서 결정했다 (L1, 라이언에게 올리지 않는다)

QA 가 코드 6 항목 전부 PASS 를 냈고, 대신 판정을 요구하는 것 둘을 남겼다.

### 결정 1 — 반올림 자릿수는 지금 코드가 맞다. SPEC 을 고쳤다

`창 1M · 11.7%` 이 아니라 `창 1M · 12%` 로 나온다. 코드는 10% 미만에서만 소수 첫째 자리를
쓴다 (`pct<10? toFixed(1) : round`).

**코드를 그대로 둔다.** 이유 둘이다. 라우팅 판단이 0.3 퍼센트포인트로 갈리는 일은 없고,
반대로 3% 짜리 세션들이 전부 `0%` 로 뭉개지면 "작은 창으로 충분했다" 는 정보가 사라진다.
지금 규칙은 그 둘을 정확히 나눈 자리에 있다. 틀린 것은 SPEC 의 Verify 문장이었고
(내가 이 지시서에 `11.7%` 라고 적은 것이 그대로 옮겨 갔다), 그것을 고쳤다.

### 결정 2 — 날짜 경계는 이번에 건드리지 않는다. SPEC 문구만 고쳤다

QA 가 잡았다. 토큰 뷰의 날짜 경계는 KST 가 아니라 `Settings.displayTimeZone` 이고,
`cm.timeZone` 이 `"system"` 이라 이 맥에서는 **IST(Asia/Calcutta)** 다.

**이번 작업에서 바꾸지 않는다.** 이 경계는 창 점유가 만든 것이 아니라 토큰 뷰의 모든
숫자 — 토큰 합계, 비용, `AI 가동`, `리드` — 가 이미 쓰고 있는 것이다. 여기서 KST 로
옮기면 이번 변경과 무관한 숫자가 전부 같이 움직이고, 그러면 이 작업의 회귀 판정
(7 일치 바이트 동일)이 통째로 무의미해진다. 창 점유는 **두 번째 경계를 만들지 않았다** 는
것이 옳은 상태이고, 그것을 SPEC EP-19 에 명시했다.

다만 라이언이 화면에서 보고 있는 `시각 Asia/Calcutta (UTC+5.5) 기준` 이 의도한 것인지는
**별개 항목이다.** 이 지시서에서 하지 않는다 — 하면 이 일이 자란다. 큐에 새 항목으로
올려야 할 발견으로 보고에 한 줄만 남긴다.

### 그리고 하나 고쳤다 — 없는 것을 약속하던 툴팁

`DashboardContent.swift:3445` 의 일 행 툴팁이 옛 응답에서도 "그날 세션들의 창 점유 분포"
를 약속하고 있었다. 분포는 안 그려지는데 툴팁만 남아서, 없는 것을 찾느라 행을 뒤지게
된다. 툴팁을 `dist` 가 있을 때만 그 문구를 붙이도록 조건부로 바꿨다. 빌드 통과.

완성 — 토큰 뷰 세션 행마다 `창 1M · 62%` 가 색과 함께 보이고, 823K 세션이 400% 가 아니라 82% 로 나오며, 창을 모르는 모델은 숫자를 지어내지 않고 `창 —` 로 남는다.
