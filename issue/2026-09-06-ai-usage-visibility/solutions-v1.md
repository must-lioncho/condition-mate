# 솔루션 후보 S1

작성일: 2026-09-06 · 기반: [I1](intent-v1.md), [P1](problem-v1.md) · 상태: 비교 초안, 미선택

아래는 설계 가설이다. 현재 서비스가 특정 API를 제공한다거나 특정 로컬 파일에 한도 값이 있다고 확인한 문서가 아니다. 실제 구현 가능성은 후속 검증이 필요하다.

## 데이터를 얻는 후보

| 후보 | 접근 | 의도에 기여하는 점 | 제약·미확인 사항 | 다음 검증 및 제외 조건 |
|---|---|---|---|---|---|
| A · 서비스 직접 연동 | 제공되는 공식 사용량 경로가 있다면 서비스별로 연결한다 | 출처가 분명한 값을 독립적으로 표시할 수 있다 | 계정 상품에 맞는 한도·리셋 필드 및 인증 지원 여부 미확인 | 공식 문서와 실제 응답 비교. 원하는 지표를 제공하지 않으면 해당 서비스에서는 제외 |
| B · 기존 도구의 결과 활용 | 기존 사용량 도구가 노출하는 로컬 데이터·CLI·인터페이스를 읽는다 | 이미 동작하는 수집을 재사용할 수 있다 | 사진 속 도구의 제품·버전·출력 경로 미확인. 기존 미지원도 물려받을 수 있다 | Antigravity·GLM의 실제 값이 있는지 확인. 없다면 두 서비스 해결책으로는 제외 |
| C · 서비스 앱/CLI의 로컬 상태 활용 | 해당 앱이 실제로 저장하거나 노출하는 한도 정보를 읽는다 | 로컬에서 얻는 경로가 있으면 별도 조회 동선을 줄일 수 있다 | 데이터 존재·정확성·유효기간·계정 연결 모두 미확인 | 서비스 화면과 대조. 세션 토큰만 있으면 한도 데이터 경로로는 제외 |
| D · 계정 사용량 페이지 읽기 | 인증된 사용량 화면의 값을 읽어 표시한다 | 별도 API가 없어도 접근 가능한 화면이 있다면 후보가 된다 | 로그인 만료·화면 변경·자동 조회 허용 범위·운영 부담 확인 필요 | 대상 화면과 반복 조회 가능성 확인. 유지 부담이 과하면 보류 |
| E · 수동 값/바로가기 | 사용자가 값을 기록하거나 서비스 사용량 화면으로 이동한다 | 완전 연동 전 확인 동선을 줄일 수 있다 | 자동 최신 값이라는 목표를 충족하지 못한다 | 사용자가 임시 대안으로 받아들일 때만 채택. 전체 완료로 간주하지 않음 |
| F · 로그 기반 추정 | 기존 토큰 집계를 재사용한다 | 과거 사용량을 보는 별도 목적에는 도움이 된다 | 구독 한도의 분모·산정 규칙이 없으면 사용률·리셋을 만들 수 없다 | I1의 핵심이 한도라면 단독 해법에서 제외. 토큰이 핵심으로 확인되면 재평가 |

서비스별로 서로 다른 경로를 조합할 수 있다. 예를 들어 A+B 또는 A+C가 가능하다는 뜻이지, 특정 서비스에 어느 경로가 동작한다고 정한 것은 아니다. 후보 수를 이 여섯 가지로 제한하지 않는다.

## 화면을 구성하는 후보

| 후보 | 사용 방식 | 장점 | 판단할 점 |
|---|---|---|---|
| U1 · 앱 하단 요약 + 팝오버 | 사진처럼 한 줄을 보고 눌러 상세를 연다 | 참고 이미지의 확인 동선에 가장 가깝다 | 어느 컨디션 메이트 창에서 항상 보일지, 좁은 폭 처리 |
| U2 · macOS 메뉴바 + 팝오버 | 다른 앱에서 작업할 때도 사용량을 연다 | 컨디션 메이트 화면 밖에서도 확인 가능하다 | 사용자가 말한 ‘하단’과 다른 배치이므로 적합성 확인 필요 |
| U3 · 대시보드 요약 + 상세 패널 | 기존 토큰 화면 등과 연결해 상세를 본다 | 계정과 기간별 설명 공간을 확보하기 쉽다 | 사용량 확인을 위해 화면 이동이 늘어나는지 |

사용자가 제공한 이미지에는 Detailed/Compact, 새로고침, 서비스별 행, 이력·계정 관리 진입점이 보인다. 모두 구현 필수로 확정하지 않는다. 우선 요약과 상세라는 구조를 검토하고 나머지는 의도 기여도로 판단한다.

## 공통 표현의 초안

서비스와 계정 아래에 그 서비스가 실제 제공하는 한도 항목을 배치한다. 5시간·주간·모델별 한도를 모든 서비스에 강제로 적용하지 않는다. Gemini와 Antigravity가 같은 계정 또는 한도를 공유한다고도 가정하지 않는다.

예상 상세 행: `서비스 / 계정 / 한도 항목 / 사용 또는 잔여 % / 초기화 시점 / 마지막 성공 시각 / 상태`.

사용률로 통일하려면 해당 값이 같은 한도 풀의 잔여율인지 먼저 확인해야 한다. 리셋이 미확인이면 시간을 추정하지 않는다. 한 계정 안의 한도 여러 개나 여러 계정의 퍼센트를 더하거나 평균 내어 전체 사용률을 만들지 않는다.

값이 없을 때는 ‘연결 필요’, ‘조회 실패’, ‘지원 경로 미확인’을 구분하고, 마지막 성공 값이 있으면 그 시각과 함께 오래된 값임을 표시하는 방안을 검토한다. 이런 상태 표현은 정직한 UI를 위한 조건이며, Antigravity·GLM의 실제 사용량 확보를 대신하지 않는다.

## 아직 선택하지 않는 이유와 후속 판단 순서

1. I1의 해석이 맞는지 확인한다. 한도와 토큰 중 무엇을 원하는지가 우선이다.
2. 대상 상품·계정을 정하고, 서비스별 한도 값·리셋·출처·시각을 실제로 얻을 수 있는지 작은 범위에서 검증한다.
3. P1을 유지하거나 P2를 쓴다. 데이터 접근이 가능한데 동선이 문제라면 UI에 무게를 둔다.
4. 의도 충족 범위, 정확성, 갱신 안정성, 유지 부담으로 후보를 비교하고 S2를 쓴다.

이 순서는 후속 검토 제안이다. 이번에는 연결 실험이나 구현을 실행하지 않는다.

## 변경 이력

- S1: 수집 경로 6개와 화면 구성 3개를 독립 후보로 작성. 선택·구현 없음.
