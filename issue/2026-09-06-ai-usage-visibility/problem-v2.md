# 문제 정의 P2

작성일: 2026-09-06 · 기반: [I2](intent.md) · 상태: 검증 전 가설

## 문제 한 문장

사용자가 여러 AI 서비스의 계정별 한도 사용 현황을 컨디션 메이트의 한 화면에서 일관되게 읽을 수 없어, 특히 Antigravity와 GLM은 얼마나 사용했고 언제 다시 사용할 수 있는지 파악하기 어렵다.

이는 사진과 사용자 발언을 해석한 정의다. 실제 관심이 한도보다 누적 토큰이나 비용이라면 이 정의를 수정해야 한다.

## 관측한 것

| 근거 | 관측 | 여기서 단정할 수 없는 것 |
|---|---|---|
| 사진 1·2 | 짧은 사용량 요약과 서비스별 상세 패널이 있다. Claude와 Codex에는 사용률·리셋 정보가 보인다 | 해당 값의 정확성, 갱신 주기, 수집 방식 |
| 사진 2 | Antigravity는 `Usage unavailable`, Gemini는 `Refresh failed`다 | 인증 문제인지, 일시 오류인지, 데이터 경로 미지원인지 |
| 사진 2·사용자 발언 | 사진에 GLM 행이 없고 사용자가 GLM 미지원을 말했다 | 컨디션 메이트에도 GLM 관련 기능이 전혀 없다는 결론 |
| 현재 코드 | GLM 계정 등록과 토큰 화면의 GLM 분류가 있다 | GLM 구독 한도까지 읽는다는 결론 |
| 현재 코드 | Antigravity 세션 로그의 문자 수로 토큰을 추정해 집계한다 | 서비스가 산정한 사용량이나 남은 한도와 같다는 결론 |

코드 근거: [AntigravityTokenCollector.swift](../../Sources/ConditionMate/Core/AntigravityTokenCollector.swift), [LLMAccountStore.swift](../../Sources/ConditionMate/Core/LLMAccountStore.swift), [토큰 집계](../../Sources/ConditionMate/AppDelegate.swift), [토큰 화면](../../Sources/ConditionMate/Dashboard/DashboardContent.swift).

정적 코드 확인만 수행했다. 앱을 실행해 실제 값이나 계정 연결 상태를 확인하지 않았고, 서비스의 현재 API 제공 여부도 조사하지 않았다.

## 문제 목록과 우선순위

문제의 원인이 확정되지 않아도 조사 순서는 정할 수 있다. **현재 1순위는 Antigravity와 GLM의 한도 데이터를 실제로 확보할 수 있는지 확인하는 것이다.** 두 서비스 사이의 선후는 아직 정하지 않았으며 둘 다 같은 최우선 대상이다.

| 순위 | 문제 | 먼저 다루는 이유 | 다음 단계로 넘어갈 근거 |
|---|---|---|---|
| 1 | Antigravity·GLM의 실제 지원 가능성이 미확인이다 | 불가능하거나 제약이 크면 전체 솔루션과 범위가 달라진다. 뒤늦게 알면 UI·기존 서비스 연동 작업이 낭비될 수 있다 | 각 서비스의 대상 상품·계정, 조회 경로, 실제 얻은 값, 인증·구독 조건, 남은 제약을 근거와 함께 판정 |
| 2 | 확보한 값이 원하는 한도 사용률·리셋 정보인지 불명확하다 | 값이 있어도 세션 토큰이나 다른 상품의 한도면 목적을 충족하지 못한다 | 공식 화면/응답과 지표 의미·한도 기간·계정·갱신 시각 대조. 1순위 조사에서도 이 구분을 함께 확인 |
| 3 | 필요한 정보가 서로 다른 화면·형식에 흩어져 있다 | 실제 확보 가능한 정보가 정해져야 적합한 공통 화면을 설계할 수 있다 | 1·2순위 결과를 반영한 표시 항목과 요약·상세 동선 |
| 4 | Claude·OpenAI 등 기존에 표시되던 서비스까지 통합해야 한다 | 통합 가치는 있지만 이번 요청의 가장 큰 불확실성을 해소하지 못한다 | Antigravity·GLM 판정과 그에 따른 범위 결정을 마친 뒤 통합 검토 |

사진에 나오는 기존 서비스의 값은 컨디션 메이트 연동이 검증됐다는 뜻은 아니다. 4순위에서도 별도 검증이 필요하다.

## 1순위 확인의 완료 조건

Antigravity와 GLM을 **각각** 아래 양식으로 판정한다. API가 존재한다는 설명이나 연결 코드만으로 완료하지 않는다.

- 대상 상품·계정·모델/한도 그룹: 어떤 사용량을 확인했는가.
- 확보 경로와 접근 조건: 공식 API, 앱/CLI 상태, 사용량 페이지 등 어디에서 어떻게 얻는가. 필요한 구독·구매·인증 조건이 있는지도 구분한다. 구매 필요 여부 확인은 구매 실행을 뜻하지 않는다.
- 실제 증거: 조회 시각, 비밀정보를 제외한 응답/화면, 얻은 필드와 의미, 원본 사용량 화면과의 일치 여부.
- 판정: **가능 / 조건부 가능 / 조사한 범위에서 불가 / 미확인**.
- 제약과 남은 질문: 반복 갱신, 계정 구분, 특정 필드 누락, 추가 접근 필요 여부.

현재 두 서비스 모두 **미확인**이다. 사진의 미표시나 기존 도구의 미지원은 서비스 자체의 데이터 접근 불가능을 입증하지 않는다. 한 경로가 실패했다고 모든 경로가 불가능하다고 단정하지 않는다.

## 판정 후 진행 규칙

- 둘 다 가능: 2순위 지표 검증 결과를 정리하고 공통 표현·통합 후보를 구체화한다.
- 조건부 가능: 조건과 유지 부담이 의도를 충족하는지 판단한 뒤 진행 범위를 정한다.
- 하나라도 불가 또는 미확인: 원인·조사 범위·남은 경로를 기록하고 문제/솔루션을 다시 정의한다. Claude·OpenAI 구현으로 우회해 전체 목표가 진행된 것처럼 처리하지 않는다.

이 선행 확인이 끝나기 전에는 Claude·OpenAI 연동, 공통 UI 구현, 정교한 화면 설계에 자원을 먼저 투입하지 않는다. 문서의 UI 후보는 보관된 아이디어이며 착수 순서를 뜻하지 않는다.

## 만족 여부를 판단할 기준 초안

1. Antigravity와 GLM을 포함한 대상 서비스가 공통 요약·상세 구조에 나타난다.
2. 값에는 계정, 한도 대상/기간, 사용 또는 잔여의 의미, 리셋 시점이 식별된다. 서비스가 제공하지 않는 필드는 미확인으로 보인다.
3. 수집 실패, 연결 안 됨, 지원 경로 없음, 오래된 값이 0%와 구분된다. 확인된 실패 원인만 표시한다.
4. 최신 값인지 판단할 수 있도록 마지막 성공 시각과 현재 갱신 상태를 알 수 있다.
5. 토큰 추정치로 한도 사용률을 대신하지 않는다. 값을 못 얻었다면 해당 서비스의 사용량 표시 목표는 미달성으로 남긴다.

정확도 허용 범위와 갱신 간격은 아직 정하지 않았다.

## 다음 버전으로 바뀔 수 있는 근거

| 확인할 내용 | 답에 따라 바뀌는 것 |
|---|---|
| 사용자가 주로 판단하려는 것이 잔여 한도, 누적 토큰, 비용 중 무엇인가 | 핵심 지표와 문제 문장 |
| GLM 상품과 계정, Antigravity 계정·모델 그룹은 무엇인가 | 수집 대상과 한도 단위 |
| ‘같은 인터페이스’가 뜻하는 배치·조작 범위는 어디까지인가 | 요약 표시 위치와 상세 동선 |
| 각 서비스에서 실제로 얻을 수 있는 값과 갱신 조건은 무엇인가 | 접근 문제의 원인과 가능한 후보 |

이 항목들은 다음 검토의 질문이며, 이번 문서 작업을 중단시키는 승인 요청이 아니다.

## 변경 이력

- P1: 문제를 나열했으나 우선순위와 선행 확인의 완료 조건이 없었다.
- P2: 사용자 정정 반영. Antigravity·GLM 지원 가능성을 1순위로 정하고, 기존 서비스 통합보다 먼저 확인하도록 진행 조건 추가. 실제 지원 여부에 관한 새 검증 결과는 없음.
