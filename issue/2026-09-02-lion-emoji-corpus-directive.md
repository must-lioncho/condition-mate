## 0. 시작 전에 PO 가 실측한 것 — 원문의 전제 두 개가 틀렸다

지시서를 쓰기 전에 코드와 원장과 슬랙 API 를 직접 열었다. 그 결과 원문이 전제로 깔고
있던 것 두 개가 실측과 어긋났다. 워커는 **원문이 아니라 이 절의 값**을 쓴다.

### 0-1. 오염 구간은 "최근 1주일" 이 아니다 — 두 개의 다른 오염원이 있다

원문은 "마지막 1주일은 데몬이 라이언 토큰으로 리액션을 달았으니 제외한다" 고 했다.
실측하면 오염원이 둘이고, 오래된 쪽이 훨씬 크다.

**오염원 A — 데몬 `ack-emoji`.** 원장 `~/.condition-mate/slack-translate/actions-daemon.jsonl`
의 `ack-emoji` 첫 줄은 `at: 1788140884` = **2026-08-31 10:48:04 KST** 이고 현재 196건이다.
원문이 어림한 1주일이 아니라 **약 2.5일**이다.

**오염원 B — 앱의 처리완료 미러 ✅. 이것이 진짜 문제다.**
`Sources/Plugins/Slack/SlackTranslateStore.swift:92` 에 `doneEmoji = "white_check_mark"` 가
있고, `syncReaction`(`:624-652`)이 라이언이 대시보드에서 항목을 처리완료로 누를 때마다
**슬랙 원문에 ✅ 를 라이언의 xoxp 토큰으로 단다.** 원장 `actions.jsonl` 의
`api.reactions.add` 는 **2026-07-24 10:42 → 2026-09-01 21:41**, 505행이다.

> **정정 (워커 1 실측, 2026-09-02).** PO 가 위 505행 전체를 ✅ 미러로 읽은 것은 과잉이었다.
> `detail` 을 뜯어보면 **✅ 미러의 실제 시작은 2026-08-17 16:10** 이고, 7/24 부터의
> `api.reactions.add` 는 ✅ 가 아니라 `done.unset` 의 **👀 트리거 복원**이었다.
> 그러므로 ✅ 오염 구간은 6주가 아니라 **2.5주**다. 또 505행 중 한 id 가 385회 반복된
> 재시도 루프라 **고유 항목은 92개**다(§0-2 표의 "512" 는 행 수).
> **방법은 그대로 옳다** — 날짜가 아니라 id 로 자르는 것이 여전히 유일하게 정확한 필터다.
> 워커 1 이 제거 로그에만 있고 추가 로그에 없는 id 120개를 추적해 완결성까지 검증했고,
> `detail` 에 ✅ 추가·복원이 적힌 99행은 **전부 286 안에 있다(누락 0)**.

이것을 모르고 학습하면 "라이언은 ✅ 를 압도적으로 많이 쓴다" 는 결론이 나오는데,
그것은 라이언의 습관이 아니라 이 앱의 UI 동작이다. 자기 출력을 학습하지 말라는
원문의 경고가 겨냥한 자리가 원래 여기다.

### 0-2. 그래서 제외는 날짜가 아니라 **항목 id** 로 한다

날짜 컷오프는 오염원 B 를 못 막는다(6주에 걸쳐 흩어져 있다). 대신 앱과 데몬이
**자기가 무엇에 리액션했는지를 id 로 기록해 두었다.** 그 목록을 그대로 제외 집합으로 쓴다.

| 제외 집합 | 어디서 | 건수(9/2 기준) |
|---|---|---|
| 앱이 단 ✅·👀 | `~/.condition-mate/slack-translate/reactions.json` 의 키 | 88 |
| 앱 액션 로그 | `actions.jsonl` 의 `reaction.add` · `api.reactions.add` 의 `id`/`detail` | 512 |
| 데몬 선응답 | `actions-daemon.jsonl` 의 `ack-emoji` 의 `id` | 196 |

셋을 합집합하면 **286개의 고유 항목 id** 다(중복 제거 후, PO 실측).

**가정 A1 — 제외는 항목 단위이지 리액션 단위가 아니다.** 한 메시지에 라이언과 기계가
각각 다른 이모지를 달았을 수 있고 그러면 라이언 것까지 같이 버린다. 그래도 이렇게 한다.
슬랙 API 는 리액션이 언제 누구의 의도로 달렸는지를 주지 않으므로 리액션 단위로 가르는
방법이 없다. **오염을 남기는 것보다 진짜 데이터를 조금 버리는 쪽이 싸다.**

**가정 A2 — 날짜 컷오프는 추가로 두지 않는다.** id 제외가 날짜 제외를 포함한다.
원문의 "마지막 1주일 제외" 는 이 id 제외로 대체한다.

### 0-3. 슬랙 API 는 3개월치를 준다 — 확인했다

`reactions.list` 를 `cm-slack-user-token`(xoxp) 으로 실제로 호출했다.
`auth.test` → `ok:true, user_id: U03GRE909MJ, team: MUST Company`.
`limit=100 · cursor` 로 12페이지(1200건)를 받았고 그 지점의 가장 오래된 메시지 ts 가
**2026-07-28 18:53 KST** 였으며 `next_cursor` 가 아직 남아 있었다.
3개월(약 2026-06-03 까지)이면 대략 40~60페이지다. 페이지당 0.3초를 두면 30초 이내다.

**주의 — `reactions.list` 는 리액션을 단 시각을 주지 않는다.** 주는 것은 메시지의 `ts` 뿐이다.
그래서 기간 필터는 **메시지 ts** 기준이고, "리액션을 언제 달았나" 로는 자를 수 없다.
이것이 0-2 에서 날짜가 아니라 id 로 자르기로 한 두 번째 이유다.

### 0-5. 🙏 · 👌 · 👍 · 🙇 는 어휘집에 있는데 **한 번도 나갈 수 없다** — 코드 결함

`Sources/Plugins/Slack/Daemon/emoji-layer.mjs:362`:

```js
if (heavy) return wrap('R1', back, `어휘집 "${heavy.label || heavy.name}" 일치 · 물음·요청 신호 없음 → :${back?.name}:`, 'not-needed');
```

`matchHeavy` 는 `level0 !== true` 인 자동 이모지(🙇 🙏 👌 👍)를 찾는다. 그런데 찾고 나서
돌려주는 행이 매치된 `heavy` 가 아니라 **`back`(= ✅)** 이다. 즉 "🙏 로 받아야 할 자리다"
라고 정확히 판정한 다음 ✅ 를 단다. 어휘집에 뜻을 정성껏 적어 둔 이모지 네 개가
구조적으로 절대 슬랙에 나가지 못한다.

코드의 주석은 이것을 의도라고 적는다("뜻이 무거운 이모지는 자동으로 달지 않는다").
그리고 **테스트가 이 동작을 명시적으로 지키고 있다** —
`emoji-layer.decision.test.mjs:104-109`, "무거운 어휘(👌 승인)는 등급 R1 · 표식 ✅ 로
예전 그대로다". 즉 이것은 드리프트가 아니라 9/2 배치가 의식적으로 남긴 가드다.
(`router.md` §1-4 의 "✅ 또는 그 어휘가 지목한 이모지" 는 `matchLevelZero` 경로 —
🫡 처럼 `level0:true` 인 행 — 로 이미 충족되므로 문서가 깨진 것도 아니다.)

**그러나 그 가드가 지금은 너무 넓다.** 라이언이 이번에 이름을 댄 세 이모지 중 하나가
🙏 인데, 🙏 는 `level0` 이 아니라 heavy 라서 **구조적으로 절대 나갈 수 없다.**
가드를 그대로 두면 이 배치가 라이언이 지목한 것을 못 만든다.

**가정 A3 — 가드를 없애지 않고 둘로 쪼갠다.** 지금 heavy 는 "뜻이 무겁다" 한 덩어리인데,
실제로 위험한 것은 무거움이 아니라 **승인·동의의 뜻을 갖는가**다.

| 이모지 | 뜻 | 자동으로 달면 | 이 배치의 처리 |
|---|---|---|---|
| 👌 `ok_hand` | 승인 (상대가 APPROVE 로 읽는다) | **9/2 사고보다 나쁘다** | ✅ 로 계속 접는다 |
| 👍 `+1` | 동의 | 라이언의 판단을 참칭한다 | ✅ 로 계속 접는다 |
| 🙏 `pray` | 기원 — 내가 해 줄 것이 없다 | 승인 뜻이 없다 | **자기 자신으로 나간다** |
| 🙇 `man-bowing` | 겸손 · 송구 | 승인 뜻이 없다 | **자기 자신으로 나간다** |
| 🙌 `raised_hands` | 환호 (신규, §0-4) | 승인 뜻이 없다 | **자기 자신으로 나간다** |

가르는 값은 **코드에 박지 않고 어휘집에 적는다.** 이 파일이 이모지 뜻의 정본이라는 규칙
(`emoji-layer.mjs:27-31`)을 새 축에도 그대로 적용한다. 행에 `approval` 을 두고 `:362` 는
이렇게 판정한다.

```js
const fold = heavy.approval !== false;   // 접지 않는 것은 명시적으로 false 일 때뿐이다
const row  = fold ? back : heavy;
```

**부호 방향이 핵심이다.** `approval === true` 일 때 접는 것이 아니라 **`false` 가 아니면
접는다.** 키가 없으면 접힌다. 이유 둘 — (1) 누군가 heavy 행을 생각 없이 추가했을 때
라이언 계정으로 승인이 나가는 쪽이 아니라 ✅ 가 나가는 쪽으로 떨어져야 한다.
(2) `approval` 을 모르는 옛 어휘집은 전 행이 접히므로 **오늘 동작과 바이트 단위로 같다.**
PO 가 반대 방향(`=== true` 로 접기)을 먼저 짜 봤는데, 옛 어휘집에서 👌·👍 가 자기 자신으로
나가 버렸다 — 하위 호환이 안전한 쪽이 아니라 위험한 쪽으로 떨어졌다. 그래서 뒤집었다.

**PO 실측 — 이 설계를 스크래치패드 사본에서 실제로 돌려 확인했다.**
`emoji-layer.mjs` · `slack-emoji-layer.json` · `emoji-layer.decision.test.mjs` 를 복사해
위 패치를 얹고 `node --test` 를 돌렸다.

| 검사 | 결과 |
|---|---|
| 기존 테스트 18개 | **18 pass / 0 fail** |
| `"Approved, go ahead."` (👌) | `white_check_mark` — **여전히 접힌다** |
| `"Sounds good to me."` (👍) | `white_check_mark` — **여전히 접힌다** |
| `"Good luck! Hope it goes well."` (🙏) | `pray` — **자기 자신으로 나간다** |
| `"화이팅! 잘 되기를 응원합니다"` (🙏 한국어) | `pray` |
| `"잘 부탁드립니다"` (🙇) | `bow` |
| `"Understood, thanks"` (level0) | `white_check_mark` — 그대로 |
| `"I'll proceed accordingly"` (level0) | `saluting_face` — 그대로 |
| `approval` 키를 전부 지운 옛 어휘집 | 위 다섯 개가 **전부 `white_check_mark`** — 오늘 동작 |

즉 **`:104-109` 가드 테스트가 그대로 통과하고**, 하위 호환도 안전한 쪽으로 떨어지며,
라이언이 지목한 🙏 가 실제로 나간다. 원문이 금지한 "L0~L5 분기 신설"(G5)도 아니고
모델 호출도 늘지 않는다(G4 준수).

워커 2 는 이 패치를 그대로 옮기면 된다. 스크래치패드 사본은 세션이 끝나면 사라지므로
**증거가 아니라 참고**다 — 워커 2 는 레포에서 다시 돌려 같은 표를 브리프에 싣는다.
`emoji-layer.mjs` 의 `:361-362` 두 줄을 아래 블록으로 통째로 바꾼다. 이것이 PO 가
실제로 돌려서 위 표를 낸 그 코드다.

```js
  const heavy = matchHeavy(t, cat);
  if (heavy) {
    // 접지 않는 것은 어휘집이 approval:false 라고 명시했을 때뿐이다. 키가 없으면
    // 접는다 — 새 행을 생각 없이 추가했을 때 라이언 계정으로 승인이 나가는 쪽이
    // 아니라 ✅ 가 나가는 쪽으로 떨어져야 한다. 옛 어휘집도 이 경로로 오늘과 같다.
    const fold = heavy.approval !== false;
    const row = fold ? back : heavy;
    const note = fold ? ' (승인 뜻이라 :white_check_mark: 로 접음)' : '';
    return wrap('R1', row, `어휘집 "${heavy.label || heavy.name}" 일치 · 물음·요청 신호 없음 → :${row?.name}:${note}`, 'not-needed');
  }
```

어휘집 쪽은 heavy 행마다 `approval` 을 **명시한다**(키를 비워 두지 않는다).
`ok_hand: true` · `+1: true` · `pray: false` · `man-bowing(bow): false` ·
`raised_hands: false`. 새로 넣는 heavy 행도 반드시 하나를 적는다.

## 1. 이 배치가 실제로 푸는 문제

라이언이 본 증상은 "리액션이 전부 🔍" 다. 원인은 세 겹이다.

1. **양성 근거 목록이 얇다.** 어휘집이 못 잡으면 `unknown` → 🔍 다(브리프 §1-4: 158건 중
   근거가 잡힌 것 26건). 이것은 원문이 정확히 짚었다.
2. **잡아도 ✅ 로 뭉개진다.** §0-5. 원문은 이것을 몰랐다.

## 5. 분류·규칙화 사양 (워커 1)

### 5-1. 최소한 이 축으로 묶는다

물음인가 통보인가 · 라이언이 답을 해야 하는가 · 상대가 누구인가(상하·내외·봇) ·

**🫡 와 ✅ 와 🙏 가 갈리는 실제 경계선을 찾는 것이 이 단계의 목적이다.** 세 이모지의

### 5-2. 규칙은 결정적이어야 한다 (G4)

**모델을 새로 부르지 않는다.** 각 이모지의 규칙은 어휘·패턴 매칭으로 표현 가능해야 하고,
그렇게 표현되지 않는 것은 **채택하지 말고 "못 잡는다" 라고 적는다.** 못 잡는다고 적은 것이
다음 배치의 입력이다. 억지로 정규식을 만들어 넣으면 오탐이 라이언 계정으로 나간다.

각 규칙에 대해 **정밀도**를 실측으로 낸다 — 그 정규식을 3개월 clean 코퍼스 전체에 돌려
`(그 이모지를 실제로 단 건) / (정규식에 걸린 건)`. 이 숫자 없이 어휘집에 넣지 않는다.

**가정 A4 — 채택선은 정밀도 0.70, 표본 8건 이상.** 실측 근거가 아니라 판단이다.
근거: 지금 어휘집에서 정당하게 나간 것이 158건 중 26건(16%)이므로 0.70 은 그보다
네 배 이상 엄격하다. 이 선에 못 미치면 어휘집에 넣지 않고 브리프에 "못 잡는다" 로 적는다.

### 5-3. 라이언이 안 쓰는 이모지를 넣지 않는다

"있으면 좋을 것 같아서" 는 사유가 아니다. clean 표본이 §5-2 의 하한(8건)에 못 미치는
이모지는 뜻만 어휘집에 적고 `auto:false` 로 둔다.

### 5-4. `man-bowing` 이름 교정

어휘집의 `bow` 행은 실제 사용 이름과 다르다(§0-4). 이름을 `man-bowing` 으로 바꾸되
**슬랙 워크스페이스에 그 이름이 실재하는지 `emoji.list` 로 확인하고** 바꾼다.
확인 안 되면 바꾸지 않고 브리프에 적는다.

## 6. `decision` · `resolves` 정합 (워커 1 실측 → PO 판정)

**이 배치에서 제일 위험한 자리다.** 9/2 사고의 본질은 이모지 모양이 아니라 "의사결정이
필요한 글이 리액션 하나로 처리완료가 되어 미처리 목록에서 사라진 것" 이다. 어휘집을
두껍게 하면서 `resolves: true` 를 헤프게 주면 같은 사고가 다른 이모지로 재발한다.

### 6-1. `decision` 은 규칙이 이미 정한다

새로 넣거나 되살리는 이모지마다 `decision` 을 반드시 적는다. 어휘집 일치로 골라지는
행은 정의상 `not-needed` 다(양성 근거가 잡혔다는 뜻이므로). `needed`·`unknown` 은
어휘집이 아니라 veto 와 바닥값이 정하므로 새 행에는 붙지 않는다.

### 6-2. `resolves` 는 **실측으로 정한다** — 이것이 §7 의 멈춤을 없애는 방법이다

"의심스러우면 false" 는 옳지만 그것만으로는 모든 새 이모지가 false 가 되고, 그러면
라이언의 미처리 목록이 영원히 안 줄어든다. 대신 코퍼스가 답을 가지고 있다.

**측정: 라이언이 그 이모지를 단 뒤, 같은 스레드(또는 같은 채널의 그 메시지 이후)에
라이언이 다시 글을 썼는가.** 다시 썼으면 그 리액션은 대화를 닫지 못한 것이고,
안 썼으면 닫은 것이다.

이모지별로 **후속 발언율** = `(리액션 뒤 라이언이 그 스레드에 다시 쓴 건) / (clean 표본)`
을 낸다. 판정선은 이렇게 둔다.

| 후속 발언율 | `resolves` |
|---|---|
| ≤ 0.20 | `true` — 라이언이 그 이모지로 실제로 끝냈다 |
| > 0.20 | `false` — 그 이모지 뒤에도 일이 남았다 |
| 표본 < 8 | `false` — 모르면 미처리에 남긴다 |

**가정 A5 — 0.20 은 판단이다.** 다섯 번에 한 번 이상 말이 더 나왔으면 그 이모지는
"끝" 이 아니라 "일단 표시" 라고 본다. 실측 분포가 0.20 근처에 뭉쳐 있어 선이 의미를
잃으면 그때 §7 로 간다.

### 6-3. 기존 행도 같이 잰다

✅ 🫡 👌 👍 🙏 🙇 는 지금 `resolves` 키가 없어 **처리완료로 읽힌다**
(`slack-emoji-layer.json` 의 `_axis_doc`). 이 여섯도 §6-2 로 재고, 선을 넘는 것은
`resolves:false` 를 **명시적으로 적는다.** 값을 안 적는 것과 true 를 적는 것을
구별할 수 있게 이 배치에서 전부 명시한다.

**단, ✅ 는 §0-1 오염원 B 때문에 clean 표본이 신뢰도가 낮다.** ✅ 의 실측은 참고로만 쓰고
현재 값(`resolves` 미지정 = true)을 바꾸지 않는다. 바꾸려면 §7 로 간다.

## 12. SPEC 편집 — 새 동작은 SPEC 항목 없이 나가지 않는다

기대 동작의 정본은 `docs/specs/SPEC.md` 다. 이 배치는 기존 세 항목과 맞물린다.

**SLKST-7 은 고치지 않는다.** 읽어 보면 이 배치와 충돌하지 않는다 — "`not-needed` 만이
`white_check_mark` 를 달 수 있는 유일한 상태다" 는 ✅ 를 달 수 있는 **상한**을 정한 것이지
`not-needed` 이면 반드시 ✅ 를 달라는 말이 아니다. heavy → ✅ 접기는 SPEC 이 아니라
테스트에만 적혀 있었다(§0-5).

**SLKST-8 은 고치지 않는다.** `resolves:false` 행이 항목을 처리완료로 만들지 않는다는
규칙 그대로다. 이 배치는 그 규칙을 쓰는 행을 늘릴 뿐이다.

**SLKST-9 는 이 배치가 지켜야 하는 게이트다.** "같은 규칙이 산문(`router.md`)과 결정값
(`slack-emoji-layer.json`)에 두 벌 적혀 있고 둘이 갈라지면 회귀다." 그래서 어휘집에
`approval` 축을 넣으면 `router.md` §1-4 표도 같이 고쳐야 한다. 한쪽만 고치면 SLKST-9 위반이다.

### 새로 넣는 항목 — SLKST-10

`docs/specs/SPEC.md` 의 SLKST-9 바로 뒤에 넣는다. 문안은 이 폴더의 관행대로 EN/KO/근거/Verify
네 줄을 갖춘다. 뜻은 이것이다.

> **SLKST-10 — 승인 뜻을 갖는 이모지만 ✅ 로 접는다.**
> 어휘집의 heavy 행(`level0 !== true`)이 일치했을 때, 그 행이 **`approval: false` 라고
> 명시했을 때만** 일치한 행 자신을 내보내고, 그 밖에는 `white_check_mark` 로 접어 내보낸다.
> 판정은 `heavy.approval !== false` 다. **`=== true` 로 뒤집으면 회귀다** — `approval` 키가
> 없는 옛 어휘집과 새로 추가된 미선언 행이 전부 자기 자신으로 나가게 되고, 그 방향의 실패는
> 라이언 계정에서 나가는 승인이다. 모르면 접는 쪽이 안전한 쪽이다.
> 👌 `ok_hand`(승인)와 👍 `+1`(동의)는 `approval: true` 여야 한다 — 이 둘을 자동으로 다는 것은
> 9/2 사고보다 나쁘다. 리액션이 라이언의 xoxp 로 나가므로 상대는 그것을 라이언의 승인·동의로
> 읽는다. 반대로 🙏 `pray`(기원) · 🙇 `man-bowing`(겸손) · 🙌 `raised_hands`(환호)는 승인 뜻이
> 없으므로 자기 자신으로 나간다. 이 셋을 ✅ 로 접는 것도 회귀다 — 라이언이 그 자리에서 실제로
> 쓰는 말을 대신 못 하게 된다.
> 판정을 `emoji-layer.mjs` 에 이름으로 박으면 회귀다. `approval` 은 JSON 에서 읽는다
> (SLKST-7 의 "이모지 이름은 JSON 에서 읽는다" 와 같은 이유).
> **Verify** 는 `emoji-layer.decision.test.mjs` 의 기존 18개 + 신규 3개 통과와
> §8 의 원장 196건 재판정 수치로 채운다.

### 어휘집 자체가 SPEC 이 아니다

어휘집에 어떤 이모지가 몇 건 실측으로 들어갔는지는 SPEC 에 적지 않는다. 그것은 데이터이고

## 실행 순서

1. **수집.** 슬랙 API 로 라이언(U03GRE909MJ)의 리액션을 3개월치 뽑는다. 리액션만이 아니라

   매핑이 선다. 이모지만 세면 빈도표가 나오고 규칙은 안 나온다.
2. **분류.** 이모지별로 어떤 메시지 유형에 붙었는지 묶는다. 최소한 이 축은 봐라 —
   물음인가 통보인가, 라이언이 답을 해야 하는가 아닌가, 상대가 누구인가(상하·내외),
   메시지 길이, 채널이냐 DM 이냐. 🫡 와 ✅ 와 🙏 가 갈리는 실제 경계선을 찾아라.
3. **규칙화.** 각 이모지에 대해 결정적으로 판정 가능한 조건을 쓴다. **모델을 새로 부르지
   않는다** — `manifest.md` G4 가 그렇게 정했다. 어휘·패턴 매칭으로 잡히지 않는 규칙은
   채택하지 말고 못 잡는다고 적어라.
4. **`decision` 축과의 정합.** 새로 넣는 이모지마다 `decision`(not-needed/needed/unknown)과
   `resolves`(true/false)를 반드시 정한다. **여기가 이 배치에서 제일 위험한 자리다.**
   9/2 사고의 본질은 이모지 모양이 아니라 "의사결정이 필요한 글이 리액션 하나로
   처리완료가 되어 미처리 목록에서 사라진 것" 이다. 어휘집을 두껍게 하면서 `resolves: true`
   를 헤프게 주면 그 사고가 다른 이모지로 재발한다. 의심스러우면 `resolves: false` 다.
5. **대조 검증.** 원장 `ack-emoji` 158건에 새 어휘집을 다시 돌려, 그중 몇 건이 🔍 에서
   벗어나는지와 **그 판정이 라이언이 그 자리에서 실제로 뭘 했는지와 맞는지**를 센다.
   숫자만 내지 말고 틀린 건을 몇 개 그대로 보여라.
6. **시험 배치.** `slack-emoji-layer.json` 의 `_doc` 에 적힌 운영 오버라이드 경로

   레포 JSON 을 바로 고치기 전에 이 경로를 쓸지는 판단해서 정하고 근거를 남겨라.

## 1초 요약

요구 — 라이언 본인이 3개월간 실제로 쓴 슬랙 이모지를 전량 학습해 어휘집을 두껍게 하고, 레이어 1 짧은 글에서도 감정 표현이 나가게 한다.
문제 — 리액션이 전부 🔍 인 것은 어휘집이 얇아서만이 아니다. 어휘집이 라이언이 지목한 🙏 를 정확히 골라내도 코드가 그것을 ✅ 로 접어 버려 구조적으로 나갈 수 없고(`emoji-layer.mjs:362` 의 heavy 가드가 승인 이모지와 감정 이모지를 한 덩어리로 묶었다), 어휘집이 적어 둔 사용 빈도가 실측과 반대이며(🙌 를 "안 쓴다" 로 적었는데 실제 46건으로 👍 보다 많다), 학습 데이터로 쓰려던 최근 6주치 ✅ 는 라이언의 어휘가 아니라 앱이 처리완료 도장으로 찍은 것이다 — 세 겹을 다 걷어야 감정 표현이 화면에 보인다.
완성 — 3개월 clean 코퍼스가 파일로 남고, 표본 8건·정밀도 0.70 을 넘긴 이모지가 `decision`·`resolves` 를 명시한 채 어휘집에 서고, heavy 가드가 `approval` 축으로 쪼개져 🙏 는 나가고 👌 는 계속 접히며, 원장 196건 재판정에서 🔍 이탈 건수와 오판 5건이 브리프에 원문 그대로 실린다.
