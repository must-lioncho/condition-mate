# Slack 번역 미처리 227건 — 상태축을 4개로 가르고 백로그를 마감한다

상태: 구현

`Slack 번역` 탭의 미처리가 227건이라 라이언이 다 볼 수 없다. 그래서 슬랙에 다시 들어가
확인하게 되고, 같은 메시지를 두 번 확인하는 구조가 됐다. 세그 토글을 4개로 가르고
파이프라인 도입 전 백로그를 되돌릴 수 있게 마감해, 매일 보는 화면을 227건에서 10건으로
줄인다.

## 문제

세 가지가 겹쳐 있다.

**첫째, 미처리 227건이 읽을 수 없는 크기다.** 읽을 수 없으니 라이언은 대시보드를 신뢰하지
않고 슬랙으로 간다. 대시보드가 슬랙을 대체하려고 만든 화면인데 슬랙을 한 번 더 열게 만들고
있으니, 기능이 목적과 반대로 작동한다.

**둘째, "AI가 처리한 것" 과 "라이언이 슬랙에서 손으로 이모지를 단 것" 이 뭉뚱그려져 있다.**
`autoDone` 938건의 `autoBy` 최다값이 `U03GRE909MJ` 606건이고 이 id 는 라이언 본인이다
(`people-directory.json` → `realName: "Lion cho (조중현,Cho Chung Hyun)"`). UI는 둘 다
`✅ 이모지로 해결됨` 으로 표시한다. 화면이 라이언 자신의 노동을 자동화 성과로 되돌려 주고
있어서, AI가 실제로 무엇을 해 줬는지 화면에서 알 수 없다.

**셋째, 미처리 안에 성격이 다른 것이 섞여 있다.** 오늘 판단해야 할 것과 나흘 전에 쌓인
분류 불가분이 같은 줄에 서 있다.

## 실측 (2026-09-01 · `items.jsonl` 1670줄 전수)

전체 1670 = `autoDone` 938 + `done.json` 만 505 + 미처리 227. 합이 정확히 맞는다.

미처리 227건을 두 축으로 교차 집계했다.

| | AI가 슬랙에 행동함<br>(`ackAt`) | 등급만 매김<br>(`ackGrade`/`requestLevel`) | 아무 흔적 없음 |
|---|---|---|---|
| **08-29 이후** | 24 | 9 | 1 |
| **08-28 이전** | 0 | 0 | **193** |

`requestLevel`·`ackGrade` 부여 파이프라인은 **08-29에 도입**됐다. 그 이전 수집분은 등급이
0건이고, 위 표의 왼쪽 아래 두 칸이 0인 것이 그 결과다. 193건은 AI가 등급도 응답도 남기지
않은 파이프라인 도입 전 백로그다.

부가 수치:
- source 분포 — dm 142, mention 69, broadcast 2
- `later` 플래그 0건, `ackGrade` 없음 222건
- 08-29 이후 유입 234건 중 미처리 34건 = **신규 유입분 미처리율 14.5%**
- 08-29 이후 `requestLevel` 분포 — L2=83, L0=58, L4=34, L3=31, L1=1
- 08-29 이후 `ackGrade` 분포 — R1=87, R2=11, R0=4

읽을 것은 두 가지다. **신규 파이프라인은 이미 잘 돌고 있다** (미처리율 14.5%). 그리고
**화면을 막고 있는 것은 신규 유입이 아니라 과거 193건**이다.

## 결정

### 라이언의 3-상태안만으로는 10.6%밖에 줄지 않는다

라이언은 세그 토글을 `AI 처리 / 결정 대기 / 전체` 3개로 나누고 60% 이상 감소를 기대했다.
실측상 이 기대치는 성립하지 않는다.

분류는 **이미 처리된 것을 다른 칸으로 옮길 뿐, 처리되지 않은 것을 줄이지 못한다.** 그러니
분류로 줄일 수 있는 최대치는 "미처리 중 이미 AI 손을 탄 것의 비율" 로 처음부터 고정돼
있고, 그 값이 24/227 = **10.6%** 다. 227 → 203이 된다. 칸을 몇 개로 나누든 이 상한을 넘을
수 없다.

193건이 전부 `결정 대기` 로 떨어지기 때문이다. AI가 판정한 흔적이 없으니 `AI 처리` 로 보낼
근거가 없다.

### 그래서 축을 하나 더 얹는다 — 세그 4개 + 백로그 마감

라이언의 축을 버리지 않는다. `AI 처리`/`결정 대기` 구분은 옳다. 다만 그 사이로 떨어지는
193건을 받을 칸을 하나 더 만든다.

| 칸 | 정의 | 적용 후 건수 |
|---|---|---|
| **결정 대기** (기본) | done 아님 · 백로그 아님 · `ackAt` 없음 | **10** |
| **AI 처리** | `ackAt` 있음 | 24 |
| **백로그** | `backlogClosedAt` 있음 | 193 |
| **전체** | 전부 | 1670 |

**227 → 10. 감소율 95.6%.** 라이언이 기대한 60%를 넘긴다. 실제 지렛대는 분류가 아니라
백로그였다.

분류 계약은 위에서 아래로 한 번만 판정한다.

```js
if (doneMap[it.id] || it.autoDone) return 'done';
if (it.backlogClosedAt)            return 'backlog';
if (it.ackAt)                      return 'ai';
return 'wait';   // 결정 대기
```

08-29 이후 등급만 매기고 응답까지 못 간 9건은 `결정 대기` 로 간다. AI가 보고서 행동하지
않기로 한 것이므로 사람이 판단해야 할 것이 맞다.

### 처리완료 칩을 사람과 AI로 가른다

라이언의 두 번째 요구에 대한 답이다. `autoBy` 가 자기 자신인지를 데몬이 `autoByMe` 로
기록하고, UI가 이것으로 칩을 가른다.

- `autoByMe === true` → `✅ 내가 슬랙에서 처리`
- `autoByMe === false` → `✅ 다른 사람이 처리`
- `autoByMe === undefined` → `✅ 이모지로 해결됨` (옛 레코드 — 모르는 것은 모른다고 둔다)
- `ackAt` 있음 → `🤖 AI 응답함` 칩을 추가로 단다

`undefined` 를 `false` 로 뭉개지 않는다. "다른 사람이 했다" 와 "누가 했는지 모른다" 는
다른 사실이다.

### 백로그 마감은 되돌릴 수 있어야 한다

`Scripts/slack-backlog-close.mjs` 로 처리한다.

- 기본이 `--dry-run` 이다. `--apply` 를 줘야 쓴다. `--undo` 로 되돌린다.
- 쓰기 전에 `items.jsonl` 을 `items.jsonl.bak.<타임스탬프>` 로 백업한다.
- `done.json` 을 건드리지 않는다. **슬랙에 아무것도 보내지 않는다** — 리액션도 메시지도
  API 호출도 없다. 로컬 파일만 다시 쓴다.
- 붙이는 것은 `backlogClosedAt` 과 `backlogReason: "pre-grading-pipeline"` 두 필드뿐이다.
- 기존 1670줄이 그대로 읽혀야 하고 줄 수가 변하면 안 된다. 파싱 실패한 줄은 원문 그대로
  다시 쓴다.

마감은 삭제가 아니다. 항목은 남고, 전용 탭에서 언제든 보이고, 되돌아온다. 다만 매일 보는
화면을 막지 않는다.

## 남은 개선점 — 라이언이 나중에 판단할 것

**1. 결정 대기 10건은 왜 10건인가.** 그중 9건은 AI가 등급까지 매겼는데 응답으로 가지 못했다.
등급을 매기고도 멈추는 자리가 있다는 뜻이다. 227을 10으로 줄이고 나면 이 10건이 처음으로
읽을 수 있는 크기가 된다. 다음에 볼 곳은 여기다.

**2. `requestLevel` 등급 경계가 쏠려 있을 수 있다.** L2=83, L0=58, L4=34, L3=31 인데
**L1 이 1건뿐**이다. 다섯 단계 중 하나가 사실상 안 쓰이고 있다면 그 단계는 없는 것과 같고,
경계가 잘못 그어졌다는 신호일 수 있다. 이번 범위 밖이다.

**3. 193건을 소급 등급 부여할 것인가.** 기술적으로 가능하지만 모델 호출 193회가 든다.
나흘 지난 DM·멘션에 지금 등급을 매겨서 얻는 값이 그 비용을 넘는지 확인되지 않았다.
백로그 탭에서 실제로 건질 것이 나오는지 며칠 지켜본 뒤 결정하는 편이 싸다.

**4. 백로그가 다시 쌓일 수 있는가.** 이번 193건은 파이프라인 도입이라는 일회성 사건이
원인이었다. 다음에 판정 로직을 크게 바꾸면 같은 일이 또 생긴다. 그때는 마감 스크립트를
다시 쓰지 말고, 판정 파이프라인이 바뀔 때 미분류분을 어떻게 다룰지를 규칙으로 먼저 정하는
것이 맞다.

**5. 두 번 체크가 실제로 사라졌는지는 사람만 안다.** 화면이 10건이 됐다고 라이언이 슬랙에
안 가게 되는지는 며칠 써 봐야 나온다. 만약 여전히 슬랙에서 체크한다면 원인은 건수가 아니라
다른 데 있다는 뜻이고, 그때 다시 봐야 한다.
