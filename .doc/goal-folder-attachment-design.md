# 골 번호별 폴더 · 첨부파일 관리 구조 설계

골 하나를 번호(goal-NN) 기준의 한 폴더로 묶어, 정의 문서와 첨부파일을 같은 자리에서 관리한다. 대시보드에서 골 번호를 누르면 그 골의 전용 페이지로 가서 정의와 첨부를 함께 확인한다.

- 상태: 구현됨 (2026-06-25). IssuePaths·/goal 페이지·번호 클릭·첨부 폴더 전환·정의 lazy 마이그레이션 반영.
- 작성일: 2026-06-25
- 확정 사항: 저장 위치는 `.claude/issue/goal-NN/` 통합. 정의 문서와 첨부를 한 폴더에 두고 git으로 추적·브라우징한다.
- 관련 코드: ReviewStore.Goal(seq, evidence[Evidence]), AppDelegate(evidenceDir·serveEvidence·/api/goal/evidence/*), DashboardServer(/evidence·/transcript·page 라우트), DashboardContent(gnum·evidencePanel·viewSession)
- 관련 정책: .claude/doc/sprint-policy.md, .claude/doc/time-policy.md

## 1. 배경 / 현재 상태

지금 첨부(증거, Evidence)는 두 가지 사실 위에 서 있다.

첫째, 메타데이터는 골 안에 산다. 각 골은 `evidence` 배열을 가지며, 항목은 링크(kind=link, url)거나 파일(kind=file, filename)이다. 이 배열은 goals.json에 함께 저장되어, 완료된 골도 링크·파일을 그대로 들고 있다.

둘째, 파일 바이트는 UUID 폴더에 산다. 업로드한 파일은 `<데이터디렉토리>/evidence/<goalId>/` 아래에 저장되고, `/evidence/<goalId>/<evidenceId>` 경로로 다운로드된다. 여기서 goalId는 골의 내부 키인 UUID다.

셋째, 화면은 인라인 펼침이다. 대시보드는 골마다 증거 패널을 펼쳤다 접으며, 링크 추가·파일 첨부 버튼을 그 안에 둔다. 골 번호는 `gnum(g)`가 seq를 받아 goal-NN으로 그리지만, 누를 수 있는 대상이 아니다.

넷째, 정의 문서는 따로 산다. 골의 서술적 정의는 `.claude/issue/goal-NN.md`로 git에 들어 있고, 런타임 골(goals.json)·첨부 저장소와는 연결되어 있지 않다.

문제는 세 가지다. 첨부가 사람이 못 읽는 UUID 폴더에 흩어져 번호로 찾을 수 없다. 정의 문서와 첨부가 서로 다른 자리에 있어 한 골을 한눈에 못 본다. 골 번호를 눌러 들어갈 자리가 없어, 첨부를 보려면 목록에서 패널을 펼쳐야 한다.

## 2. 설계 목표

골 번호 하나가 폴더 하나에 대응한다. 그 폴더 안에 정의 문서와 모든 첨부가 모인다. 사람이 파인더·git에서 번호로 바로 찾고, 대시보드에서 번호를 눌러 전용 페이지로 들어가 같은 내용을 본다. 저장은 git이 추적하는 리포지터리 안(.claude/issue)에 둬, 첨부가 코드와 함께 버전 관리된다.

## 3. 폴더 구조

루트는 `.claude/issue/`다. 골 하나마다 `goal-NN` 폴더를 둔다(NN은 seq를 두 자리로 0 채움, 예: goal-07, goal-56). 폴더 안에 다음을 둔다.

- `goal.md` — 골 정의 문서. 지금의 `.claude/issue/goal-NN.md`를 이 폴더 안으로 옮긴 것. 폴더가 골 하나의 집이 되도록 정의도 폴더 안에 둔다.
- `attachments/` — 업로드한 첨부파일의 실제 바이트가 들어가는 하위 폴더. 파일명 충돌을 막기 위해 저장명 앞에 증거 id를 붙인다(지금 규칙 유지). 원본 표시명은 메타데이터가 따로 들고 있으므로 저장명이 사람에게 보일 필요는 없다.
- `attachments.json`(선택) — 그 골 첨부의 메타데이터 사이드카. 링크 항목과 파일 항목의 표시명·추가일·종류를 담는다. goals.json을 진실의 원천으로 그대로 둔다면 생략 가능하나, git에서 폴더만 봐도 첨부 목록을 읽히게 하려면 사이드카를 권장한다(5절 미결정).

폴더 자체는 골이 새로 생기거나 seq가 처음 부여될 때 만든다. seq가 아직 0인(번호 미부여) 골은 폴더를 만들지 않고, 번호가 붙는 순간 만든다.

## 4. 정체성 매핑 — UUID와 번호

골의 내부 키는 goalId(UUID)이고, 사람이 보는 키는 seq(goal-NN)다. 첨부 폴더를 번호로 이름 붙이면 사람은 편하지만, 번호와 내부 키 사이의 매핑을 분명히 해야 한다.

원칙은 이렇게 둔다. 진실의 원천은 여전히 goalId다. goals.json의 각 골은 goalId로 식별되고, evidence 메타데이터도 골 안에 그대로 산다. 폴더 이름 goal-NN은 그 골의 현재 seq에서 파생된 사람용 별칭이다. 즉 폴더는 goalId를 가리키는 읽기 좋은 포인터이지, 새로운 식별자가 아니다.

seq가 바뀌는 경우를 정의한다. seq는 코드 주석상 생성 시 부여되는 안정값이지만, 재배치 가능성을 0으로 가정하지 않는다. seq가 바뀌면 폴더 이름도 따라 바뀌어야 한다. 이를 위해 폴더 안에 goalId를 적어 두는 표식(goal.md의 머리말이나 attachments.json의 한 필드)을 두어, 이름이 흔들려도 어느 골인지 역추적할 수 있게 한다. 앱은 기동 시 goals.json을 기준으로 폴더 이름을 현재 seq에 맞게 정렬(이름 갱신)할 수 있다.

번호 충돌은 없다고 본다. seq는 유일하므로 goal-NN 폴더는 골 하나에만 대응한다. seq 0(미부여)은 폴더를 만들지 않는 것으로 충돌 자체를 피한다.

## 5. 저장 위치의 전제 — 리포 결속

이 설계는 첨부를 데이터 디렉토리가 아니라 리포지터리 안(.claude/issue)에 둔다. 이는 의도된 선택이며, 따라오는 전제를 분명히 한다.

지금 첨부 바이트는 AppPaths.base 아래(개발 빌드는 리포의 .localdata, 설치 앱은 Application Support)에 저장된다. 새 설계는 첨부를 리포의 .claude/issue로 옮긴다. 따라서 이 구조는 앱이 해당 리포 작업 트리 위에서 도는 것을 전제한다. 개발 빌드는 devProjectRoot로 리포 루트를 알 수 있으므로 자연스럽다.

설치 앱(리포 밖)에서는 .claude/issue가 없을 수 있다. 그래서 첨부 루트를 한곳에서 결정하는 규칙을 둔다. 리포 루트를 알 수 있으면(개발 빌드) `<리포>/.claude/issue`를 쓰고, 알 수 없으면 데이터 디렉토리 아래(`<데이터>/issue`)로 떨어진다. AppPaths가 base·sub를 한곳에서 정하듯, IssuePaths(가칭)가 이 루트를 한곳에서 정해 호출부가 분기하지 않게 한다.

이 결속의 득과 실을 적어 둔다. 득은 첨부가 코드·정의와 함께 버전 관리되고 사람이 git·파인더에서 번호로 바로 찾는다는 것. 실은 데이터 디렉토리 분리 모델(개발·설치·테스트가 같은 코드로 다른 저장소를 쓰는 성질)에서 첨부만 떨어져 나간다는 것. 첨부가 커지면 리포가 무거워질 수 있다는 점도 미결정으로 남긴다(5절).

## 6. 라우트 / 서버

전용 페이지 라우트를 새로 둔다. `/goal?n=NN`(또는 `/goal/NN`)이 골 하나의 전체 HTML 페이지를 돌려준다. DashboardServer는 이미 /transcript·/breakdown·/worker를 page 콜백으로 처리하므로, 같은 page 경로에 /goal을 더한다. 페이지는 다음을 담는다.

- 골 머리(번호 goal-NN, 제목, 상태, 가치·토큰·시간 같은 핵심 수치).
- 정의 문서. goal.md를 읽어 사람이 읽게 렌더(마크다운 또는 최소 서식).
- 첨부 목록. 링크와 파일을 한 목록으로 보이고, 파일은 다운로드 링크, 링크는 새 탭 열기. 추가(링크·파일)와 삭제도 이 페이지에서 가능하게 한다(인라인 패널과 같은 동작을 페이지 형태로 제공).

다운로드 경로를 정리한다. 지금의 `/evidence/<goalId>/<evidenceId>`는 그대로 유지해 깨지지 않게 하되, 내부에서 새 폴더(`.claude/issue/goal-NN/attachments/`)를 바라보도록 해석을 바꾼다. 별도로 사람이 읽기 좋은 `/goal/NN/attachments/<파일>` 형태를 더할지는 미결정으로 둔다(필수는 아님).

업로드·삭제 API는 경로만 옮긴다. `/api/goal/evidence/add`·`/api/goal/evidence/remove`는 그대로 두되, 파일을 쓰는 자리를 evidenceDir(UUID 기준)에서 골 폴더의 attachments(번호 기준)로 바꾼다. 메타데이터를 goals.json에 적는 흐름은 유지한다.

## 7. 대시보드 연동 — 번호 클릭

골 번호 라벨(gnum이 그리는 goal-NN)을 누를 수 있게 한다. 동작은 기존 viewSession(트랜스크립트 새 탭 열기) 패턴을 그대로 따른다. 번호를 누르면 `/goal?n=NN`을 새 탭으로 연다. 인라인 증거 패널은 빠른 확인용으로 남겨도 되고, 페이지로 일원화하며 접을 수도 있다(5절 미결정).

번호가 비어 있는 골(seq 0)은 클릭 대상에서 제외하거나, 누르면 번호 부여를 권하는 안내로 처리한다.

## 8. 마이그레이션

기존 데이터를 안전하게 새 구조로 옮긴다. 모든 단계는 멱등(여러 번 돌려도 같은 결과)하고, 원본을 지우기 전 복사·검증을 거친다.

정의 문서를 옮긴다. `.claude/issue/goal-NN.md`를 `.claude/issue/goal-NN/goal.md`로 옮긴다. 이미 폴더 형태면 건너뛴다.

첨부 바이트를 옮긴다. `<데이터>/evidence/<goalId>/`의 파일을, 그 goalId의 현재 seq로 정한 `.claude/issue/goal-NN/attachments/`로 복사한다. 복사가 검증되면 원본은 남겨 두거나(안전) 정리한다(택일, 5절).

하위 호환을 지킨다. 옛 다운로드 경로(`/evidence/<goalId>/<id>`)는 계속 동작해야 하므로, 서버는 새 폴더에서 먼저 찾고 없으면 옛 폴더로 떨어지는 순서로 해석한다. 마이그레이션이 끝나기 전에 열린 페이지도 깨지지 않게 한다.

## 9. 단계적 구현 순서 (구현 시)

할 일을 작은 단위로 쪼개 각 단계가 독립적으로 동작·검증되게 쌓는다.

1단계 경로 결정 한곳에 모으기. IssuePaths(가칭)를 만들어 골 폴더 루트와 goal-NN 경로를 한곳에서 정한다. 리포 결속·데이터 디렉토리 폴백 규칙을 여기 둔다.

2단계 폴더 생성·이름 정렬. 골 생성·seq 부여 시 폴더를 만들고, 기동 시 현재 seq에 맞게 폴더 이름을 정렬한다. goalId 표식을 폴더에 적는다.

3단계 첨부 저장 위치 전환. 업로드·삭제·다운로드가 골 폴더의 attachments를 바라보게 바꾼다. 옛 경로 폴백을 둔다.

4단계 전용 페이지. `/goal?n=NN` 페이지를 만들어 정의(goal.md)와 첨부를 함께 렌더한다. 추가·삭제·다운로드를 페이지에서 제공한다.

5단계 번호 클릭. 대시보드의 goal-NN 라벨을 클릭 가능하게 하고 페이지를 새 탭으로 연다.

6단계 마이그레이션. 정의 문서·첨부 바이트를 새 구조로 멱등하게 옮긴다.

## 10. 설계 선택지 / 미결정

메타데이터 사이드카(attachments.json)를 둘지 정한다. goals.json만으로 충분한지, git에서 폴더만 봐도 읽히게 사이드카를 둘지다.

옛 첨부 원본을 마이그레이션 후 지울지 둘지 정한다. 안전하게 남기면 중복 저장이 생기고, 지우면 되돌리기가 어렵다.

인라인 증거 패널을 페이지로 일원화할지 정한다. 빠른 확인용으로 패널을 남길지, 페이지로 모을지다.

리포 결속의 한계를 어디까지 받아들일지 정한다. 첨부가 커질 때 리포 비대화, 설치 앱에서 리포 부재 시의 폴백 동작 범위다.

seq 재배치 빈도를 확인한다. seq가 사실상 불변이면 폴더 이름 정렬 로직을 단순화할 수 있고, 바뀔 수 있으면 goalId 역추적을 항상 둬야 한다.

## 11. 수용 기준

- `.claude/issue/goal-NN/` 한 폴더 안에 정의(goal.md)와 첨부(attachments/)가 함께 모인다.
- 대시보드에서 골 번호(goal-NN)를 누르면 `/goal?n=NN` 전용 페이지가 새 탭으로 열린다.
- 전용 페이지에서 정의 문서와 첨부 목록을 함께 보고, 링크·파일을 추가·삭제·다운로드할 수 있다.
- 첨부 바이트가 번호 기준 폴더(goal-NN/attachments)에 저장되고, 사람이 git·파인더에서 번호로 바로 찾는다.
- 옛 다운로드 경로(`/evidence/<goalId>/<id>`)가 계속 동작한다(하위 호환).
- 골 폴더 루트가 한곳(IssuePaths)에서 결정되어, 개발 빌드는 리포 .claude/issue, 그 외는 데이터 디렉토리로 일관되게 떨어진다.
- 마이그레이션이 멱등하며, 옛 정의 문서·첨부가 손실 없이 새 구조로 옮겨진다.
